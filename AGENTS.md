# AGENTS.md

Read this first. It's the contract every agent working on this repo follows.

## Project

Drum Practice Pal: a tab-first drum practice PWA. Users upload Guitar Pro files, save bar-range loops, and track practice speed over time across phone, tablet and laptop. No original audio; playback is alphaTab's synth plus a metronome.

- Plan and unit list: `docs/plan.md`
- Handoff notes, one per unit: `docs/units/NN-name.md`

## Stack

- Vite + React 19 + TypeScript (strict, `noUncheckedIndexedAccess`)
- React Router 7 (library mode, `react-router` package)
- Tailwind CSS 4 via `@tailwindcss/vite`
- TanStack Query 5 for all server state
- alphaTab (`@coderline/alphatab` 1.9) for parsing, rendering and playback, with its Vite plugin from the separate `@coderline/alphatab-vite` package (the old `@coderline/alphatab/vite` entry is deprecated). The plugin copies fonts and the soundfont into `public/font` and `public/soundfont` on every dev and build run; those folders are gitignored
- Supabase (Postgres, auth, storage) from Unit 02
- Vitest + Testing Library; Playwright for e2e
- Hosting: Cloudflare Workers static assets via Workers Builds (`wrangler.jsonc`). Every branch and PR gets a preview URL. SPA routing is handled by `not_found_handling`, so don't add `_redirects`

## Conventions

- Named exports only, except where a tool requires a default export.
- Import from `src` with the `@/` alias across features; relative imports inside a feature.
- Colocate tests as `*.test.ts(x)` next to the code they cover.
- Pure logic (tempo math, count-in scheduling, speed conversion) lives in plain `.ts` modules with no React or alphaTab imports, so it is unit-testable without mocks.
- Components stay thin: data via hooks, logic via pure modules.
- Every query and mutation goes through TanStack Query hooks; no ad hoc fetches in components.
- Speeds are stored as a ratio (`speed_ratio`, 1.0 = original). BPM is always derived from the tempo at the relevant bar; never store BPM.
- Bar numbers in the data model and UI are 1-based. alphaTab indexes are 0-based; convert at the boundary and name variables `barIndex` vs `barNumber` accordingly.
- Comments explain why, not what.
- Check every `error` that supabase-js (and any `{ data, error }` API) returns, and throw or handle it; never destructure only `data`. This holds in scripts and test helpers too, where a swallowed error leaves users, rows or files behind.
- Never render text taken from a URL (query, fragment, `error_description`) as a message; map known codes to fixed copy. Strip the fragment from any `?next=`-style return path before using it as a redirect target.
- List APIs return one page (`auth.admin.listUsers`, `storage.list` default 100, unranged `.select()`). Loop until exhausted wherever the code needs every item. In multi-step cleanup, stop at the first failed step.
- Never commit files from `tests/fixtures/real/`.
- alphaTex: wrap metadata arguments in parentheses (`\tuning (E4 B3 G3 D3 A2 E2)`, `\ts (3 4)`). Unwrapped arguments can swallow a following `( ... )` chord. `npm run fixtures` fails on any alphaTex warning.
- alphaTab settings: always pass `core.fontDirectory: '/font/'`. Without it, production builds look for the music font next to the lazy JS chunk (`/assets/font/`) and nothing renders; dev works, so it's easy to miss. `player.soundFont` has no default, so pass an absolute path such as `/soundfont/sonivox.sf2` (or load bytes with `api.loadSoundFont`). Load alphaTab only from lazily imported routes so it stays out of the main bundle.
- Tests that read .gp files use the helpers in `tests/unit/score-helpers.ts` (`loadScoreFile`, `tempoAtBar`, `drumTrackIndex`, `playedBars`). Tests over `tests/fixtures/real/` must skip cleanly when the folder is empty (see `tests/unit/real-fixtures.test.ts`).
- Playwright specs that use DOM types inside `evaluate` start with `/// <reference lib="dom" />` (the node tsconfig has no DOM lib). alphaTab lazy-renders the score as it scrolls into view, so scroll the score container into view before asserting on notation (see `tests/e2e/spike.spec.ts`).

## Supabase

- Schema changes are new files in `supabase/migrations/` (`npx supabase migration new <name>`), never edits to applied ones. Then `npm run db:reset`, `npm run db:types`, and commit the regenerated types. CI fails if they drift.
- Every table has `user_id` and owner-only RLS (`user_id = (select auth.uid())`). Child tables reference their parent by `(id, user_id)` so a row can't point at another user's parent.
- Supabase's default privileges give `anon` and `authenticated` full access to every new public table and function. So every migration that creates one must, in the same file: enable RLS on the table, `revoke all ... from anon, authenticated`, then grant only what's needed (column-level `grant update (col, ...)` where only some columns are client-editable). For functions, `revoke execute ... from public, anon, authenticated` unless clients must call it. `anon` gets nothing. See the end of `20261122000000_schema.sql`.
- Storage: private bucket `gp-files`, objects at `{user_id}/{song_id}.gp`. Build paths with `songFilePath()` from `src/lib/schema.ts`; policies reject any other shape.
- `src/lib/schema.ts` mirrors DB limits (speed ratio 0.25 to 2.0, count-in bars, text lengths) for client-side validation; its test fails if they drift from the SQL.
- Keys: the browser gets `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` only. `SUPABASE_SECRET_KEY` bypasses RLS and is for node scripts and tests; never prefix it with `VITE_`. `.env.local` is gitignored; `.env.example` lists the names. Scripts and `tests/db` fall back to `supabase status`, so they need no env locally.
- Node-side clients and admin chores (`createAdminClient`, `createNodeClient`, `findUserIdsByEmail`, `removeUserFiles`) live in `scripts/supabase-admin.ts`, shared by the seed script and `tests/db`. Connection details come from `scripts/local-supabase.ts`.
- Database tests sign users in with the real magic-link flow (`createTestUser` in `tests/db/helpers.ts`) and clean up after themselves. Build rows with `songRow`, `sessionRow`, `insertSong` and `insertLoop`, and assert error codes with `PG.*` from the same file rather than raw strings. Local magic-link emails land in Mailpit at http://127.0.0.1:54324. Seed users: `demo@drumpal.test` and `other@drumpal.test`.

## App shell, auth and data hooks

- Routes live in `src/App.tsx`. Signed-in screens are children of the `<RequireAuth><AppShell /></RequireAuth>` layout route; `/login` and the dev-only `/spike` sit outside it. Player routes are `lazy()` so alphaTab stays out of the main bundle.
- Auth state comes from `useAuth()` (`src/lib/auth.ts`), fed by `AuthProvider` from `supabase.auth.onAuthStateChange`. Screens behind the guard call `useSignedInUser()` for the user. supabase-js refreshes tokens itself; a failed refresh arrives as `SIGNED_OUT`, which clears the query cache and the guard sends the user to `/login?next=...`. The redirect helpers (`loginPathFor`, `safeNextPath`, which rejects off-site targets, and `linkErrorFromHash`) live in `src/features/auth/loginRedirect.ts`.
- Sign-in is passwordless: one email with a magic link and a 6-digit code (`supabase/templates/sign_in.html`). The code is for phones on the LAN and installed PWAs, where the link can't open the app.
- One browser client: `supabase` from `src/lib/supabase.ts`, typed with `Database`. Env comes from the committed `.env.development` (local stack defaults) in dev and the e2e build; production builds need `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` set, or the app shows a config message. A loopback API URL is rewritten to the page's host so LAN devices reach the local stack.
- **Data hook pattern** (copy `src/features/settings/`):
  - `<feature>Form.ts` (or another pure module): the selected columns as a `const` list plus a matching select string literal (a test keeps them equal), the row type picked from `Database`, and pure validation and diff helpers. It imports no client, so the API module, components and node tests share it.
  - `<feature>Api.ts`: plain async functions over `supabase` that return typed rows and throw on error via `unwrap(result, 'what')` or `throwIfError(result)` from `src/lib/supabaseResult.ts`. Select columns with a string literal (not a joined array) so supabase-js can type the row. Always scope by `user_id` as well as relying on RLS.
  - `use<Feature>.ts`: a key factory (`settingsKeys.forUser(userId)`; every key includes the user id) plus `useQuery`/`useMutation` hooks that call the API functions. Mutations that the user sees immediately are optimistic: `cancelQueries`, `setQueryData`, roll back in `onError`, set the server row in `onSuccess`, `invalidateQueries` in `onSettled`. For a list cache, roll back only the edited item's sent fields (not a snapshot of the whole list, which undoes other writes made meanwhile), give the list's mutations one shared `mutationKey`, and invalidate in `onSettled` only when no other is pending (`isMutating({ mutationKey }) > 1` means another is in flight). See `useSongs.ts`. Where two controls can write the same item at once (a loop's "Save speed" and its edit form), `onSuccess` takes the server row whole only when no other write is pending; otherwise it takes just the fields that edit sent (`applySavedLoopEdit`, `useUpdateLoop`), because the row may be from before the other edit and would undo its optimistic values. While a form's mutation is pending, lock its inputs and ignore submits rather than calling `reset()` on edit; state the form shares with the page is locked too (`LoopEditorForm` reports `onSavingChange`, and the score picks no bars meanwhile).
  - A mutation keeps every cache of the item right, not only the list: an edit also updates the item's detail entry if one is cached (never creates one), and a delete sets the detail entry to its "not found" value and removes caches of things that went with it (`useDeleteSong` removes the downloaded file). Otherwise the item's page opens on stale data until a refetch lands.
  - Components call only the hooks. Forms keep a local draft of only the fields the user touched (`Partial<Row> | null`), render `{ ...saved, ...draft }` so refetched values show through for every other field, and send only changed fields (`changedSettings`). A field that shows a rounded value (a ratio as a whole percent) counts as changed only when what it shows changed, or saving anything rewrites the stored value with the rounded one (`changedLoopDetails`). A full-row draft would send stale values for fields another device changed.
- Component and hook tests mock the client with `vi.mock('@/lib/supabase', async () => (await import('@/test/fakeSupabase')).fakeSupabaseModule)`, call `resetFakeSupabase()` in `beforeEach`, and script answers on `fakeSupabase.auth.*`, `queryResult` (every `.single()`, `.maybeSingle()` or awaited chain; inspect sent payloads with `opArgs`) or `storageResult` (Storage `upload` / `remove` / `download`, ok by default). Render with `renderRoutes` / `wrapperFor` from `src/test/render.tsx`, which supply a retry-free QueryClient, a fixed auth state (`signedInAs`, `signedOut`, `loadingAuth`) and a `location` test id for asserting redirects. TanStack Query notifies on a timer, so wait (`findBy`, `waitFor`) after `setQueryData` instead of asserting synchronously. A test about to say that nothing changed (no notice, nothing sent again) first awaits `settle()` from the same file, after proving the thing it waited for did happen.
- Shared UI: `src/components/` (`PageHeader`, `FullPageMessage`, `ErrorAlert` for inline `role="alert"` errors such as a failed mutation, `LoadErrorAlert` for a first load that failed (`isLoadingError`) with its "Try again", class strings in `styles.ts` including `dangerButtonClass` for destructive confirms). Long pages split into one small component per step or fieldset in the same file (`LoginPage`'s `EmailStep` / `CodeStep`, `SettingsPage`'s fieldsets taking `{ values, errors, edit }`). Bottom tabs below 768 px (`md`), sidebar from 768 px; touch targets `min-h-11` (44 px) or more.
- Signed-in e2e specs import `test` and `expect` from `tests/e2e/auth.ts`, whose `user` fixture creates a throwaway user and deletes it (files first) after the test; take `{ user }` in the test's arguments rather than a module-level `let` set in `beforeEach`, so a failed setup never tears down the previous test's user. Sign in with `signIn(page, user, path)` through the real magic-link redirect. A second `browser.newContext()` is a second device; close extra contexts in a `finally`. Specs that don't sign in (smoke, spike) need no Supabase.

## Lists, files and ids (from Unit 04)

- A list the app needs in full reads every page: wrap the `.range(from, to)` query in `fetchAllPages` (`src/lib/fetchAllPages.ts`, pages of 500, under `max_rows`) and give it a total order (`.order('created_at').order('id')`). See `fetchSongs`.
- Client-chosen ids use `randomUuid()` (`src/lib/randomUuid.ts`) and hashes use `sha256Hex()` (`src/lib/sha256.ts`), never `crypto.randomUUID` or `crypto.subtle` directly: both are missing outside secure contexts, which includes a phone on the LAN dev server.
- Reading a user's Guitar Pro file goes through `parseScore` (`src/features/library/parseScore.ts`), loaded with `import()`. It runs only alphaTab's Guitar Pro importers, because `ScoreLoader.loadScoreFromBytes` falls back to alphaTex and turns junk into a one-bar score. Check bytes with `checkSongFile` first, and map problems to the fixed copy in `SONG_FILE_MESSAGES`. Refuse on `file.size` before `file.arrayBuffer()`, so an oversized pick is never read into memory.
- File plus row writes (`uploadSong`, `deleteSong` in `songsApi.ts`): upload the file, insert the row, and remove the file again if the insert fails (and say so if that removal fails too). Delete the file first, then the row, so a failure leaves the song listed and retryable rather than an unreachable file. A cancel is honoured only before the insert starts.
- Destructive actions confirm inline in the item (`SongListItem`'s `ConfirmDelete`), with no modal, and aren't optimistic.
- Search and sort that should survive going back live in the URL (`useSearchParams`, `replace: true`), validated against a known list (`isLibrarySort`). Never echo the query back as a message.
- Keep list search and sort in their own pure module (songList.ts: searchSongs, sortSongs), separate from the form module's columns and edit validation.
- Build in-app links that take a parameter with the helpers in src/lib/routes.ts (songPath(id)), not template strings. UI copy shared by two components (NO_DRUM_TRACK_NOTE) lives in a pure module, not exported from a component file.
- `tests/fixtures/gp/no-drums.gp` is a guitar-only fixture for the null `drum_track_index` path; `repeats.gp` (Unit 08) has a repeat, so two of its bars play twice.

## Player (from Unit 05)

- Every screen that plays a song uses `usePlayer` (`src/features/player/usePlayer.ts`) and the shared `PlayerControls`. The song page keeps Play/Pause (`PlayPauseButton`, with `PlayerControls showPlayButton={false}`) in a sticky bar beside the Speed/BPM readout, so both stay on screen when Play scrolls the score into view on a phone; e2e finds Play/Pause on the page, not in the controls region. Don't create `AlphaTabApi` anywhere else (the Unit 01 `/spike` page is the one exception). `usePlayer({ fileBytes, drumTrackIndex, initialOptions })` returns `scoreRef` and `scrollRef` (render both on the first render), `player` (a `PlayerService`, null while alphaTab loads) and `snapshot`. It reads its inputs once and disposes the service on unmount, so key the component by song id to load another song.
- `PlayerService` (`PlayerService.ts`) owns playback state and talks to alphaTab only through the `PlayerEngine` interface (`playerEngine.ts`). `alphaTabEngine.ts` is the only player module that imports alphaTab, and `usePlayer` loads it with `import()`. New alphaTab features go into the engine interface first, then the service.
- Service API: `load`, `play` / `pause` / `togglePlay` / `stop`, `seekToBar`, `showBar`, `setRange({ startBar, endBar } | null)` (1-based, throws `RangeError` for bars the song lacks; validate with `isValidBarRange` first), `setLooping`, `setSpeed`, `setMetronomeOn`, `setMetronomeVolume`, `setTrackMuted`, `setDrumsMuted`, `setDrumsOnly`, `setLayout`, `setHighlight` (Unit 08, see Loops), `dispose`, and `tempoAtBar(barNumber)`. `setDrumsOnly(true)` silences every track but the drum track (`snapshot.drumsOnly`; off on open, not a setting, a no-op without a drum track). It and `drumsMuted` are never both on: turning either on turns the other off. It overrides the per-track mutes from `setTrackMuted` without changing them, so off restores what was there; send a track's mute to the engine only through `applyTrackMute`, which asks `isTrackSilenced`. `seekToBar` shows the new bar in the snapshot at once, and returns false and moves nothing for a bar outside the range that is set (alphaTab clamps such a seek but reports the bar asked for, then stops reporting positions). Typed events via `player.on('position' | 'barChanged' | 'loopWrapped' | 'finished' | 'barTapped' | 'barsDragged', handler)`, which returns its unsubscribe; call it in the effect's cleanup. `barTapped` only reports a tap on a rendered bar; the screen decides what it does (jam mode seeks, `useJamMode`), and while a loop's bars are being picked they pick bars instead (see Loops).
- Live changes (speed, metronome, mute, range, looping, layout) set engine properties only; they must never stop, play or reload. The service tests assert this with `engine.restartCalls()`.
- Call `player.play()` / `togglePlay()` straight from the click handler with nothing awaited first: iOS only starts Web Audio inside the gesture. The service also sets `navigator.audioSession.type = 'playback'` there (silent switch) and holds a Screen Wake Lock while playing (`wakeLock.ts`, best effort).
- Player failures are a `PlayerError` code mapped to fixed copy in `playerMessages.ts`; never show alphaTab's message.
- alphaTab methods that return a boolean (`load`, `loadSoundFont`) report refusal that way, with no event; check it and fail, or the page waits forever. Work the engine starts (fetches) is aborted in `destroy()`.
- A screen that unmounts its content on a query error checks `isLoadingError`, not `isError`, so a failed background refetch never tears down what is already showing (a playing song).
- Speed is a ratio clamped to the DB bounds (`speed.ts`: `clampSpeedRatio`, `ratioToPercent`, `percentToRatio`). Starting options come from `user_settings` via `playerOptionsFromSettings`; every song opens at 100%.
- Tempo and BPM (from Unit 06): `tempo.ts` (pure): `barStartTempos(score)` (the tempo each bar starts at; a mid-bar change counts from the next bar), `tempoAtBar(tempos, barNumber)`, `bpmAtSpeed(tempo, ratio)` (whole BPM). The engine sends the tempos with `scoreLoaded`; the snapshot's `barTempo` is the tempo at the current bar, so displayed BPM is `bpmAtSpeed(snapshot.barTempo, snapshot.speedRatio)`. For a loop, use `player.tempoAtBar(startBar)`.
- Taps on the score: `alphaTabEngine` listens for `click` (not pointerdown, so panning never seeks) and hit-tests with `barIndexAtPoint` (`barHitTest.ts`, pure) over `api.boundsLookup.staffSystems`. alphaTab's own interaction stays off.
- alphaTab draws its cursors unstyled. The score box carries the `jam-score` class, which `src/index.css` styles (bar and beat cursor, pointer cursor). A new score container needs that class or the cursor is invisible.
- Bars and ticks: `barTicks.ts` (`barRangeToTicks`, `barIndexAtTick`, `startTickOfBar`), working on alphaTab's tick cache in play order. Layout: `layoutForWidth` / `PAGE_LAYOUT_QUERY` (`layout.ts`, pure), page from 768 px, horizontal below; `useLayout()` (`useLayout.ts`) watches the breakpoint for React.
- Test the service and hook with `FakePlayerEngine` from `src/test/fakePlayerEngine.ts` (`finishLoading({ barTempos })`; `TEMPO_CHANGE_BAR_TEMPOS` mirrors the tempo-change fixture; `soundingTracks()` replays every mute sent and gives the tracks left sounding, which is what mute tests assert rather than the calls): `new PlayerService(engine, {...})` directly, or `usePlayer({ ..., createEngine: fakeEngineFactory(engine) })`. Fire alphaTab's events with `engine.fire(...)` or `engine.finishLoading()`, wrapped in `act` in component tests.
- Song data for the player: `useSong(id)` (row, null for no such song) and `useSongFile(id)` (bytes from Storage, `staleTime: Infinity`, under `songFileKeys`, so song edits never re-download it). The fake client answers Storage `download` through `storageResult` with `{ data: new Blob([...]), error: null }`. Check a URL id with `isUuid` before querying; Postgres errors on a malformed uuid.
- e2e for the player: `openFixture` in `tests/e2e/playerPage.ts` uploads a fixture through the library, then waits for Play to be enabled (score, MIDI and soundfont loaded) before asserting; the same file has the shared locators (`controls`, `playButton`, `muteDrumsButton`, `drumsOnlyButton`, `speedSlider`, `status`, `viewport`, `barNumber`), the score-box helpers (`scoreBox`, `barCursorBox`, `scrollScoreToStart`, `windowScrollSettled`, `untilStill`) and the layout oracle (`layoutForWidth`, `expectedLayout(page)`), so specs don't repeat the 768 px breakpoint. `jam.spec.ts` taps bars by the position of alphaTab's `.at-cursor-bar` and checks the beat cursor stays on screen while playing. `drums-only.spec.ts` reads which MIDI channels alphaTab's synth has muted by recording the `alphaSynth.*` messages posted to its worker (`recordSynthMessages`, `mutedChannels`); alphaTab never resets those mutes itself, a reload included. Those message names are alphaTab internals, so a test that reads the recorder first asserts something it must have recorded; an empty log must fail, not pass.

## Count-in (from Unit 07)

- Timing is pure: `countIn.ts` (`countInSchedule({ bars, meter, tempo, speedRatio, startTime })` gives click times, accents and the downbeat; `beatSeconds`, `barMeters(score)`, `meterAtBar`, `countsInEveryRepeat`). One click per beat of the meter (6/8 is six eighths). The engine sends each bar's meter with `scoreLoaded` (`barMeters`), next to `barTempos`.
- `countInRunner.ts` (`startCountIn(output, run, { onBeat, onDownbeat })`, returns a cancel) plays a schedule on a `ClickOutput` (`clickOutput.ts`). The web output is its own `AudioContext`, since alphaTab's isn't public API. Timers are only wake-ups that re-check the output's clock; never time audio off `setTimeout` alone. `PLAY_START_LEAD_SECONDS` is how early `engine.play()` is called so playback is heard on the downbeat; tune it by ear there, not in callers.
- `PlayerService` has a `countingIn` status between `ready` and `playing`, `snapshot.countIn` (`{ bar, beat, bars, beatsPerBar }` or null) for the counter, and `setCountInBars` / `setCountInMode`. Playing or counting in is "running": test it with `isRunning(snapshot.status)` from `PlayerService.ts` (Pause shown, score on screen), not the two statuses inline. A control that starts playback is enabled on `canPlay(player, snapshot)` (`controlGates.ts`: `isLoaded`, ready or running), never on `barCount` alone: the score loads before the MIDI and the soundfont, and `play()` does nothing until they are in. `pause()`, `stop()`, `setRange()` and `load()` call a count-in off; `seekToBar()` restarts it for the new bar; `setCountInBars(0)` ends it and plays at once; speed and other count-in changes apply from the next count-in. Until the engine reports `playing`, `cancelCountIn === null` under `countingIn` means the engine has already been told to play (past the downbeat): anything that halts or fails there must stop the engine too (`callOffCountIn`, used by `pause()` and `setRange()`). A user's pause or stop sets `haltRequested` until the next `play()` or `load()`, so an event already on its way from the worker (`finished`) can't restart what the user just stopped, whether it lands before or after the engine's own "stopped"; new code that starts playback from an engine event checks it.
- A count-in uses the tempo and meter of the bar playback starts on, times the current speed: the bar under the cursor for Play (a mid-bar position is first moved back to its bar line), `range.startBar` for a repeat.
- "Before every repeat" works on `setRange` + `setLooping`: while it is on, the service keeps the engine's own looping off (`applyLooping`), so alphaTab stops and rewinds at the end of each pass, `loopWrapped` fires, and the service counts in and calls `engine.play()` again. Unit 08 only sets a range and looping. Don't read `engine.setLooping` as the user's choice; `snapshot.looping` is.
- Anything that must make sound later than the tap (the count-in's clicks, then `engine.play()` from a timer) is unlocked inside the tap: `play()` calls `clicks.unlock()` and `engine.unlockAudio()` before starting the count-in.
- UI: `CountInCounter` (the big number) goes inside a `relative` wrapper around the score viewport, not inside the scrolling box. Count-in copy shared with Settings is in `countInLabels.ts`. The controls bar's selects use `selectClass` from `src/components/styles.ts`.
- Tests: pass `clicks: new FakeClickOutput()` (`src/test/fakePlayerEngine.ts`) to `PlayerService` and use `vi.useFakeTimers()`; its clock follows `Date.now()`, so `vi.advanceTimersByTime` moves the count-in along. Service tests that involve a count-in or a loop start from `src/test/countInPlayer.ts` instead of building their own: `setupCountIn({ options, barTempos, meter, barMeters, loaded })`, `loopingBars5To8(setup)`, the engine steps `enginePlays` / `engineFinishesPass`, `clickOffsets`, and the timing constants (`START_DELAY_MS`, `LEAD_MS`, `BAR_MS`). `PlayerService.countIn.test.ts` has the worked examples; `PlayerService.countInEdges.test.ts` the tables (every cancel path, every moment). The runner fires a beat up to 2 ms early, so leave a margin around a beat rather than asserting on the exact millisecond.
- `window.__drumPalPlayer` (`debugPlayer.ts`) is the mounted `PlayerService` in dev and the e2e build, never in production: debug hooks are gated on an allow-list of `import.meta.env.MODE` values (`development`, `test`), written out in full so Vite drops the code from every other build. Use it in QA and e2e to watch the service (`count-in.spec.ts` records every status through its `debugPlayer(page)` handle) and for service features whose UI is a later unit's; remove a use once real UI exists (that spec's loop is now saved through the loop panel).

## Loops (from Unit 08)

- Feature folder `src/features/loops/`, on the data hook pattern: `loopForm.ts` (columns, `Loop`, `parseLoopForm`, `formBarRange`, `changedLoopFields`, `changedLoopDetails` for the edit form, `revertLoopEdit`, `applySavedLoopEdit`, `sortLoops`, `barsLabel`), `loopsApi.ts`, `useLoops.ts` (`useLoops(songId)`, `useCreateLoop`, `useUpdateLoop`, `useDeleteLoop`). - Speed: `speed.ts` also has `bpmToRatio(bpm, tempo)` (the exact ratio, to 6 decimals, never a whole percent), `nudgeSpeedRatio(ratio, percentDelta)`, `parseSpeedPercent` and `parseSpeedBpm`. A loop's BPM is `bpmAtSpeed(player.tempoAtBar(loop.start_bar), ratio)`; show a speed with `speedLabel(ratio, tempo)` from `loopLabels.ts` ("71% (85 BPM)"). The controls bar's slider still moves in whole 5% steps; compare ratios, never percents, to tell whether a speed is saved.
- Page state is `useLoopPractice(player, snapshot, loops)` (`useLoopPractice.ts`): `activeLoop`, `playLoop(loop)` (range, looping, saved speed, seek, play, all inside the tap; on the loop already active it is "Restart loop" and keeps the speed playing now, so an unsaved nudge isn't lost), `selectLoop(id)` (the same without speed or play), `openLoop(loop)` (the loop and its saved speed without play, for arriving by link), `exitLoop()`, and the loop form's bars (`editor`, `openEditor`, `closeEditor`, `setEditorBars`, and `setEditorSaving`, which stops taps and drags changing the bars while the form's save is pending). - Taps and drags: while the form is open (`practice.editor !== null`) taps pick bars (`tapBar` in `rangeSelection.ts`, pure) and the page passes `seekOnTap: false` to `useJamMode`; any new use of `barTapped` must make the same either-or choice. The engine reports a mouse drag across bars as `barsDragged` (`{ startBar, endBar, done }` from the service, ascending) and no `barTapped` follows it, wherever it ends; touch never drags, it scrolls. Moves are heard on the window, so a drag only reaches bars inside the scroll box's client area: the score carries on, clipped, under the box's edges. `tapGesture.ts` has the slop.

It is separate from `setRange` because the bars on show aren't always the bars playing. The engine draws it from `highlightRects` (`barHighlight.ts`, pure) into a `.bar-highlight` layer styled in `index.css`; alphaTab's own selection markers aren't used.

Anything else that moves a paused player to a bar from outside the score (Unit 09's "one tap into practice", Unit 10's keys) calls `showBar` too.

What the engine adds to the score element (the highlight layer) is taken away in `destroy()`, so a render that finishes late can't put it back.

## Practice sessions and progress (from Unit 09)

- Feature folder `src/features/practice/`: `sessionTracker.ts` (pure: the rules), `sessions.ts` (columns, `sessionInsert`, the history's wording: `durationLabel`, `practiceDateLabel`, `lastPracticedLabel`), `sessionKeys.ts` (import-free, like `loopKeys.ts`), `sessionsApi.ts`, `useSessions.ts`, `usePracticeTracker.ts` (the song page's glue), `LoopHistory.tsx`, `OnTheGoPage.tsx` (`/`). The home page's loops query lives with the loops (`practiceList.ts`, `fetchPracticeLoops`, `usePracticeLoops`).
- What a session is, in `sessionTracker.ts`: only loop practice, only while the loop sounds (`trackerPhase`: playing with the page on show; a count-in is a gap in a session, not its end; a hidden page is stopped). Logged at a stop once it has `SESSION_MIN_PLAY_SECONDS` (30) of play time; a shorter one is kept and added to. Leaving the loop (another loop, Exit loop, the loop deleted, the screen or page left) ends it: logged if long enough, dropped if not. Editing the playing loop's bars or finishing it does not end it. Its speed is the speed at the end, its repeats are `loopWrapped` events (none while the page is hidden: the hook drops those, as the tracker drops that time). The tracker is a reducer, `observe(state, { now, loopId, phase, speedRatio }, { newId })`; new rules go there with a test, not into the hook.
- `usePracticeTracker(player, snapshot, activeLoopId)` feeds it from one effect on `[activeLoopId, status, speedRatio]`. One effect on purpose: "Play loop" on another loop changes the loop and the speed in the same render, and the tracker must see them together to log the old loop at its own speed. Don't split it or drive the tracker from `player.subscribe`.
- A session has three ways out, chosen by where the page is: the hook's mutation (`useLogSession`) while the screen stays; `logSessionUnobserved` (the same mutation run from the mutation cache) as the screen unmounts, when the hook's observer is going too; `logSessionOnExit` (a `keepalive` request) from a hidden page or `pagehide`. Both `visibilitychange` and `pagehide` are listened to (iOS often fires only the first); the first ends the session and the second finds nothing. All three send the same row and tell the caches through `sessionLogged`. A keepalive that failed is sent again through the mutation, or through `logSessionUnobserved` if the screen has unmounted since (`screenGone`): never call a hook's `mutate` after its component has gone, the mutation stays tied to the dead observer and is never collected.
- `keepaliveInsert` (`src/lib/keepaliveInsert.ts`) is the one place the app calls PostgREST without supabase-js, because supabase-js can't send `keepalive` and awaits the session before it fetches. It needs the access token in hand (`useAuth().session`, kept in a ref) and never throws. Use it only for a write that must leave from a hidden or unloading page; `supabaseRestConfig` (`src/lib/supabase.ts`) exists for it alone.
- `mutate(variables, { onSuccess, onError })` runs those callbacks for the latest call only. Where several calls of one mutation can be in flight and each needs its own answer (a retry of several unsaved sessions), use `mutateAsync(variables).then(...)` as `usePracticeTracker` does.
- Idempotent writes: a session's id is made when the session opens (`randomUuid()`), and every send is "insert, on conflict do nothing" (`upsert(..., { onConflict: 'id', ignoreDuplicates: true })`, `Prefer: resolution=ignore-duplicates`). So a retry, a keepalive that also fell back to the mutation, and Unit 11's queue can all send a record again. A foreign key error (23503) means the loop is gone: that is `loopGone`, not a failure.
- After a session is logged the server has moved the loop's `last_practiced_at`. `sessionLogged` invalidates `loopKeys.forUser` and `songKeys.forUser` (the library's "recently practiced"), each only when no write of that kind is pending, as `invalidateWhenIdle` does.
- Finish and reopen are edits of `status` through `useUpdateLoop`; `finished_at` follows in a trigger. Use `useSetLoopStatus(songId, loopId)` or the `LoopStatusButton` built on it, never `useUpdateLoop` directly: the same loop has a status control in the list, in the "Mark finished?" prompt and on the home page, and its `isPending` and `error` are read from the mutation cache (`useMutationState` with `isStatusWriteOf`), not from the control's own `useMutation`. So a press on a second control can't race the first, and a failure is still reported after the optimistic change has moved the loop to another list and unmounted the control that was pressed. Any optimistic change that moves or removes the item it was made from has this problem: a test of its failure holds the write first (`holdNext` then `failNext`), or the failure lands before React has moved anything and the test passes on a message the user would never see.
- "Mark finished?" is `hasReachedTarget(loop)` (`loopForm.ts`): the saved `speed_ratio` against `target_ratio`, never the speed playing, and compared as the whole percents the loop's line shows (`ratioToPercent` of each), not as stored ratios. A speed typed as a BPM is a fine ratio (0.708333) that shows as "71%" beside "target 71%"; a comparison of the ratios would never ask. Any "has X reached Y" between two values the UI shows rounded compares what is shown. It only asks; "Not yet" is remembered per loop and saved speed (`finishQuestionKey` in `LoopPanel.tsx`).
- `/songs/:id?loop=<id>` opens the song on that loop (`useRequestedLoop`, `loopPracticePath()` in `src/lib/routes.ts`): checked with `isUuid`, opened once per id when the score and the loops are in, ignored when it isn't one of the song's loops. It can't start playback (that needs a tap); anything else that links into practice uses the same path. It is settled against a list read since the page opened, never one cached from an earlier visit (another device may have saved the loop or changed its speed since): the hook takes the query, waits while `fetchStatus` is `fetching` until `isFetchedAfterMount`, reads a fresh cached list that lacks the loop once more, and goes by the cache when the read fails or is paused. Anything else done once per page from a query's `data` (a default picked, an item opened) waits the same way before it latches "handled", and gives way if the user has chosen for themselves meanwhile (`userChoseLoop`).
- The home page shows a loop's speed as a percent only: BPM needs the tempo at the loop's first bar, which is in the file. Its tab is in the URL (`?tab=finished`, `practiceTabFrom`).
- Dates: `practiceDateLabel(iso, now)` ("Today", "Yesterday", "3 days ago", then the date). Pass `now` in; tests build dates with local-time `new Date(y, m, d)` so they don't depend on the machine's zone.
- `window.__drumPalMinSessionSeconds` (`debugPractice.ts`) lowers the 30 seconds in dev and the e2e build, gated like `debugPlayer.ts`. e2e sets it with `shortSessions(page, 2)` (`tests/e2e/practicePage.ts`) in every spec that isn't about the minimum itself; one spec plays a real minute.
- Tests: the tracker hook is tested with only the clock faked (`vi.useFakeTimers({ toFake: ['Date'] })`, moved with `vi.setSystemTime`), so TanStack Query and Testing Library keep real timers. A hidden page is `Object.defineProperty(document, 'visibilityState', ...)` plus a `visibilitychange` event; keepalive requests are read from a stubbed `fetch` (`vi.stubGlobal`), and `fakeSupabaseModule` carries `supabaseRestConfig` and an `upsert` for them. A mutation's `onSettled` awaits its refetch, so a test that answers the refetch with a promise that never resolves leaves the mutation pending.
- e2e that changes page with a nav link waits for something of the new page before reading a list: the song page's loop panel is also a list inside `main`, and is still there for a moment (`homeList` in `practicePage.ts`).
- More test patterns from Unit 09's Test stage:
  - Effects run twice: `renderHook(..., { reactStrictMode: true })` (`renderTracker('loop-a', { strict: true })` in `usePracticeTracker.test.tsx`). Assert on counts (one log, each pass counted once), which is what a leaked listener changes.
  - `useSessions.test.tsx` tests `sessionLogged` and `logSessionUnobserved` on a bare `QueryClient`: read `getQueryState(key)?.isInvalidated`, and make "a write is pending" with a mutation built from the cache that never settles (`pendingWrite`), asserting `isMutating` saw it before asserting what was left alone.
  - "A failed background refetch keeps what is showing" (`isLoadingError`): after the refetch, first assert the query's state is `error` with its data still there, then that the list is on screen. Without the first, the test passes before the failure has been drawn.
  - Two writes to one item in a component test: `holdNext('update')` holds the first; the second then answers with a row from before the first (the table applies a change when it answers), which is the stale row the checklist's row is about (`LoopPanel.test.tsx`, "Save speed" under a pending "Mark finished").
  - A cache filled before the page mounts (`renderSong(id, queryClient)` in `SongPage.test.tsx`) is how to get "the loops are in before the player exists"; `loops.holdNext('select')` gives the other order.
  - e2e: `tests/e2e/practicePage.ts` has Unit 09's locators and steps, like `loopsPage.ts` for the panel: `sessionsOf(user)` / `loopsOf(user)` (the database, by the service role), `sessionCount(user).toBe(n)` (polls it), `sessionLogged`, `openLoopHistory`, `homeTab` / `homeList` / `homeItem`, `navLink`, `shortSessions`, `playFor(page, ms)` (waits, then pauses) and `playOn(page, ms)` (presses Play and leaves it playing). `saveLoopSpeed(page, percent)` is in `loopsPage.ts`. `recordSentSessions(page)` wraps `fetch` in an init script and records each session insert's id and whether it was sent with `keepalive` (Playwright's request events don't say); `setPageVisibility(page, 'hidden' | 'visible')` hides the page as a locked phone does. A lost response is `page.route` with `await route.fetch()` then `route.abort()`: the server has the row and the page sees a failure, which is the retry that must not log twice.

## Keyboard shortcuts and focus (from Unit 10)

- Keys are pure rules in `src/features/shortcuts/shortcuts.ts`: `KEY_BINDINGS` (key to action), `resolveShortcut(press, { focus, helpOpen })` and the input guard `focusKindOf(element)` (text fields, selects and contenteditable take every key; a range slider its arrows and page keys; buttons none, so Space is play/pause wherever focus is and Enter still presses a button). Ctrl, Cmd, Alt and Shift (except `?`) are the browser's. The overlay's rows come from the same bindings (`shortcutHelp()`); a new shortcut is a binding, a help row and a case in `useSongShortcuts`, and the tests fail if the row is missing.
- The song page's glue is `useSongShortcuts({ player, practice, loops })` (`src/features/song/`): one window `keydown` listener for the page's lifetime, reading the latest inputs from a ref and the player's state from `player.getSnapshot()` at the press. It cancels a handled key's default (and Space's keyup, which some browsers turn into a button press). Everything runs inside the key event, so Space can start audio on iOS.
- Gates: `src/features/player/controlGates.ts` (`canPlay`, `canChangeOptions`, `canUseDrumToggles`) is the one predicate per precondition, used by the button, by the action where it can refuse (`playLoop` checks `canPlay`), and by the key. A new control that starts or changes playback takes its gate from there.
- Loop keys follow the panel's order, `loopsInPanelOrder` (`loopForm.ts`, beside `loopsByStatus`, which the panel's two sections use); while running they `playLoop`, while paused they `openLoop` (set up, no sound). Nothing while the loop form is open or before the loops are read; with no loops they step a bar (`seekToBar` + `showBar`).
- A dialog is modal by hand (`ShortcutOverlay`): focus to its first control on open, Tab kept inside, Escape and a click outside close it (only a press that began outside: one begun inside and let go outside clicks the backdrop too), focus back to what had it if still on the page; the page's shortcuts are off while it is open. jsdom has no `showModal`.
- Focus when a pressed control leaves the page: `useFocusWhenReady()` (`src/lib/`) takes a finder and focuses what it returns on the first render that has it, only if focus is still on what was pressed or on `<body>`, and gives up after `FOCUS_WAIT_MS`. Buttons that stand in for one another carry data attributes with finders in `src/features/loops/loopFocus.ts` (`statusButtonAttributes` / `findStatusButton`, `editButtonAttributes` / `findFormOpener`). Schedule from the press handler, after the action said it acted (`setStatus` returns false when it sent nothing), never from an effect of the same render. A control focus may be handed to while a write is pending is locked with `aria-disabled` (styled by `buttonBase`), its handler refusing the press, never `disabled`: `focus()` on a disabled button does nothing, and the wait has ended (`LoopStatusButton`). A form that replaces a list focuses itself (`tabIndex={-1}`, `preventScroll`), not its first field, which on a phone would bring up the keyboard.
- Tests: `useSongShortcuts.test.tsx` fires keys on the focused element over `loopPlayer()` through its `renderShortcuts(loops, { loaded, drumTrackIndex, strict, loopsPending })` view (`key(k, init, target)` for a whole press, `keyDown` / `keyUp` for one half, each false when the page cancelled it; `focused(tag)` puts a focused element on the page); `SongPage.test.tsx` "keyboard shortcuts" uses `user.keyboard` (`openSong(loops, { song })`, its `playLoop(name)`, and `pressed(name)` for a toggle's `aria-pressed`). A control locked with `aria-disabled` is asserted with `expectLocked` / `expectUnlocked` (`src/test/locked.ts`), since Testing Library's `toBeDisabled` ignores it. e2e is `tests/e2e/shortcuts.spec.ts`; take focus off the last click with its `focusNothing(page)` before pressing a key that would otherwise land in a field. `metronomeButton` is in `playerPage.ts` with the other toggles.

## Stage workflow

Each unit runs Build, Test, QA, Readability, Review (see `docs/plan.md`). Each stage:

1. Reads this file, its unit section in `docs/plan.md`, earlier notes in `docs/units/`, and `docs/review-checklist.md` (the defect classes outside reviewers keep finding: interleavings, gates, gestures, round trips, validated paths). Build designs against it, Test proves its rows, Review walks every row.
2. Stays inside its unit's scope.
3. Ends with `npm run check` green (and `npm run e2e` from Unit 03 on).
4. Appends its section to `docs/units/NN-name.md`.
5. Updates this file when it sets a pattern later units should copy.
6. Adds a line to the owning unit's **Carried forward** list in `docs/plan.md` for each open issue it hands to a later unit, and deletes the lines its own unit dealt with.
