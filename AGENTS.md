# AGENTS.md

Read this first. It's the contract every agent working on this repo follows.

## Project

Drum Practice Pal: a tab-first drum practice PWA. Users upload Guitar Pro files, save bar-range loops, and track practice speed over time across phone, tablet and laptop. No original audio; playback is alphaTab's synth plus a metronome.

- Plan and unit list: `docs/plan.md`
- Who it is for and how to judge a design: `docs/product.md`. Read it before designing or building anything a user touches
- Handoff notes, one per unit: `docs/units/NN-name.md`

Remove or rewrite what the instruction replaces, so no file is left saying the old thing. Say in your reply which files you changed. If an instruction contradicts a doc and it isn't clear which should win, ask.

- Tailwind CSS 4 via `@tailwindcss/vite`

- Vitest + Testing Library; Playwright for e2e

- CI (`.github/workflows/ci.yml`): the repo is public, so GitHub-hosted runners cost nothing. `check`, e2e and `db` run on PRs (a newer push cancels the PR's running run) and on "Run workflow", not on the merge to `main`, which runs only `migrate`. `main` is protected: changes land through a PR whose checks passed, never a direct push

## Conventions

- Named exports only, except where a tool requires a default export.
- Import from `src` with the `@/` alias across features; relative imports inside a feature.
- Colocate tests as `*.test.ts(x)` next to the code they cover.
- Pure logic (tempo math, count-in scheduling, speed conversion) lives in plain `.ts` modules with no React or alphaTab imports, so it is unit-testable without mocks.
- Components stay thin: data via hooks, logic via pure modules.
- Every query and mutation goes through TanStack Query hooks; no ad hoc fetches in components.
- Speeds are stored as a ratio (`speed_ratio`, 1.0 = original). BPM is always derived from the tempo at the relevant bar; never store BPM.
- Bar numbers in the data model and UI are 1-based. alphaTab indexes are 0-based; convert at the boundary and name variables `barIndex` vs `barNumber` accordingly.
- Comments explain why, not what.
- Check every `error` that supabase-js (and any `{ data, error }` API) returns, and throw or handle it; never destructure only `data`. This holds in scripts and test helpers too, where a swallowed error leaves users, rows or files behind.
- Never render text taken from a URL (query, fragment, `error_description`) or an error's own `message` as a message; map known codes to fixed copy (`failureCopy`, see Unit 13 below). Strip the fragment from any `?next=`-style return path before using it as a redirect target.
- List APIs return one page (`auth.admin.listUsers`, `storage.list` default 100, unranged `.select()`). Loop until exhausted wherever the code needs every item. In multi-step cleanup, stop at the first failed step.
- Never commit files from `tests/fixtures/real/`.
- alphaTex: wrap metadata arguments in parentheses (`\tuning (E4 B3 G3 D3 A2 E2)`, `\ts (3 4)`). Unwrapped arguments can swallow a following `( ... )` chord. `npm run fixtures` fails on any alphaTex warning.
- alphaTab settings: always pass `core.fontDirectory: '/font/'`. Without it, production builds look for the music font next to the lazy JS chunk (`/assets/font/`) and nothing renders; dev works, so it's easy to miss. `player.soundFont` has no default, so pass an absolute path such as `/soundfont/sonivox.sf2` (or load bytes with `api.loadSoundFont`). Load alphaTab only from lazily imported routes so it stays out of the main bundle.
- Tests that read .gp files use the helpers in `tests/unit/score-helpers.ts` (`loadScoreFile`, `tempoAtBar`, `drumTrackIndex`, `playedBars`). Tests over `tests/fixtures/real/` must skip cleanly when the folder is empty (see `tests/unit/real-fixtures.test.ts`).
- Playwright specs that use DOM types inside `evaluate` start with `/// <reference lib="dom" />` (the node tsconfig has no DOM lib). alphaTab lazy-renders the score as it scrolls into view, so scroll the score container into view before asserting on notation (see `openFixture` in `tests/e2e/playerPage.ts`).

## Supabase

- Schema changes are new files in `supabase/migrations/` (`npx supabase migration new <name>`), never edits to applied ones. Then `npm run db:reset`, `npm run db:types`, and commit the regenerated types. CI fails if they drift.
- CI's `migrate` job pushes every migration to the hosted project when it reaches `main`, at about the moment Workers Builds deploys that build, so a migration must be additive: the build before it has to keep working on the new schema. The one exception, `20261129000000_drop_target_ratio.sql`, went out before the app had users. Anything that renames or drops what the live build reads takes two releases (docs/release.md, section 2). A migration whose check existing rows could fail gets its SQL check in release.md, run before merging.
- Every table has `user_id` and owner-only RLS (`user_id = (select auth.uid())`). Child tables reference their parent by `(id, user_id)` so a row can't point at another user's parent.
- Supabase's default privileges give `anon` and `authenticated` full access to every new public table and function. So every migration that creates one must, in the same file: enable RLS on the table, `revoke all ... from anon, authenticated`, then grant only what's needed (column-level `grant update (col, ...)` where only some columns are client-editable). For functions, `revoke execute ... from public, anon, authenticated` unless clients must call it. `anon` gets nothing. See the end of `20261122000000_schema.sql`.
- Storage: private bucket `gp-files`, objects at `{user_id}/{song_id}.gp`. Build paths with `songFilePath()` from `src/lib/schema.ts`; policies reject any other shape.
- `src/lib/schema.ts` mirrors DB limits (speed ratio 0.25 to 2.0, count-in bars, text lengths) for client-side validation; its test fails if they drift from the SQL.
- Keys: the browser gets `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` only. `SUPABASE_SECRET_KEY` bypasses RLS and is for node scripts and tests; never prefix it with `VITE_`. `.env.local` is gitignored; `.env.example` lists the names. Scripts and `tests/db` fall back to `supabase status`, so they need no env locally.
- Node-side clients and admin chores (`createAdminClient`, `createNodeClient`, `findUserIdsByEmail`, `removeUserFiles`) live in `scripts/supabase-admin.ts`, shared by the seed script and `tests/db`. Connection details come from `scripts/local-supabase.ts`.
- Database tests sign users in with the real magic-link flow (`createTestUser` in `tests/db/helpers.ts`) and clean up after themselves. Build rows with `songRow`, `sessionRow`, `insertSong` and `insertLoop`, and assert error codes with `PG.*` from the same file rather than raw strings. Local magic-link emails land in Mailpit at http://127.0.0.1:54324. Seed users: `demo@drumpal.test` and `other@drumpal.test`.

## App shell, auth and data hooks

- Routes live in `src/App.tsx`. Signed-in screens are children of the `<RequireAuth><AppShell /></RequireAuth>` layout route; `/login` sits outside it. Player routes are `lazy()` so alphaTab stays out of the main bundle.
- Auth state comes from `useAuth()` (`src/lib/auth.ts`), fed by `AuthProvider` from `supabase.auth.onAuthStateChange`. Screens behind the guard call `useSignedInUser()` for the user. supabase-js refreshes tokens itself; a failed refresh arrives as `SIGNED_OUT`, which clears the query cache and the guard sends the user to `/login?next=...`. The redirect helpers (`loginPathFor`, `safeNextPath`, which rejects off-site targets, and `linkErrorFromHash`) live in `src/features/auth/loginRedirect.ts`.
- Sign-in is passwordless: one email with a magic link and a 6-digit code (`supabase/templates/sign_in.html`). The code is for phones on the LAN and installed PWAs, where the link can't open the app.
- Local testing skips the email: under `npm run dev` only, the login page has "Dev: sign in as …" (`DevSignIn`), which signs in as the typed address (or `demo@drumpal.test`) with `DEV_PASSWORD` (`devPassword.ts`), creating the account on first use. Seed users get that password. It is gated on `import.meta.env.DEV && MODE === 'development'` and on `DEV_TARGET_IS_LOCAL` (`devTarget.ts`: the configured Supabase URL is loopback, checked again inside the sign-in), so a dev server pointed at a hosted project has no button and the seed gives the password only on the local stack; no build has it (the e2e build is `--mode development` but not DEV) and Vitest doesn't render it. An account first made by email has no password and gets fixed copy saying so.
- One browser client: `supabase` from `src/lib/supabase.ts`, typed with `Database`. Env comes from the committed `.env.development` (local stack defaults) in dev and the e2e build; production builds (Workers Builds, previews included) take the hosted project from the committed `.env.production`; without those two values the app shows a config message. A loopback API URL is rewritten to the page's host so LAN devices reach the local stack.
- **Data hook pattern** (copy `src/features/settings/`):
  - `<feature>Form.ts` (or another pure module): the selected columns as a `const` list plus a matching select string literal (a test keeps them equal), the row type picked from `Database`, and pure validation and diff helpers. It imports no client, so the API module, components and node tests share it.
  - `<feature>Api.ts`: plain async functions over `supabase` that return typed rows and throw on error via `unwrap(result, 'what')` or `throwIfError(result)` from `src/lib/supabaseResult.ts`. Select columns with a string literal (not a joined array) so supabase-js can type the row. Always scope by `user_id` as well as relying on RLS.
  - `use<Feature>.ts`: a key factory (`settingsKeys.forUser(userId)`; every key includes the user id) plus `useQuery`/`useMutation` hooks that call the API functions. Mutations that the user sees immediately are optimistic: `cancelQueries`, `setQueryData`, roll back in `onError`, set the server row in `onSuccess`, `invalidateQueries` in `onSettled`. For a list cache, roll back only the edited item's sent fields (not a snapshot of the whole list, which undoes other writes made meanwhile), give the list's mutations one shared `mutationKey`, and invalidate in `onSettled` only when no other is pending (`isMutating({ mutationKey }) > 1` means another is in flight). See `useSongs.ts`. Where two controls can write the same item at once (a loop's "Save speed" and its edit form), `onSuccess` takes the server row whole only when no other write is pending; otherwise it takes just the fields that edit sent, each only while the cache still holds the value it sent (`applySavedLoopEdit`, `useUpdateLoop`; 90% then 80% must not show 90% when the first answer lands), because the row may be from before the other edit and would undo its optimistic values. While a form's mutation is pending, lock its inputs and ignore submits rather than calling `reset()` on edit; state the form shares with the page is locked too (`LoopEditorForm` reports `onSavingChange`, and the score picks no bars meanwhile).
  - A mutation keeps every cache of the item right, not only the list: an edit also updates the item's detail entry if one is cached (never creates one), and a delete sets the detail entry to its "not found" value and removes caches of things that went with it (`useDeleteSong` removes the downloaded file). Otherwise the item's page opens on stale data until a refetch lands.
  - Components call only the hooks. Forms keep a local draft of only the fields the user touched (`Partial<Row> | null`), render `{ ...saved, ...draft }` so refetched values show through for every other field, and send only changed fields (`changedSettings`). A field that shows a rounded value (a ratio as a whole percent) counts as changed only when what it shows changed, or saving anything rewrites the stored value with the rounded one (`changedLoopDetails`). A full-row draft would send stale values for fields another device changed.
- Component and hook tests mock the client with `vi.mock('@/lib/supabase', async () => (await import('@/test/fakeSupabase')).fakeSupabaseModule)`, call `resetFakeSupabase()` in `beforeEach`, and script answers on `fakeSupabase.auth.*`, `queryResult` (every `.single()`, `.maybeSingle()` or awaited chain; inspect sent payloads with `opArgs`) or `storageResult` (Storage `upload` / `remove` / `download`, ok by default). Render with `renderRoutes` / `wrapperFor` from `src/test/render.tsx`, which supply a retry-free QueryClient, a fixed auth state (`signedInAs`, `signedOut`, `loadingAuth`) and a `location` test id for asserting redirects. TanStack Query notifies on a timer, so wait (`findBy`, `waitFor`) after `setQueryData` instead of asserting synchronously. A test about to say that nothing changed (no notice, nothing sent again) first awaits `settle()` from the same file, after proving the thing it waited for did happen.
- Shared UI: `src/components/` (`PageHeader`, `FullPageMessage`, `ErrorAlert` for inline `role="alert"` errors such as a failed mutation, `LoadErrorAlert` for a first load that failed (`isLoadingError`) with its "Try again", class strings in `styles.ts` including `dangerButtonClass` for destructive confirms; see Visual design below for the tokens). Long pages split into one small component per step or fieldset in the same file (`LoginPage`'s `EmailStep` / `CodeStep`, `SettingsPage`'s fieldsets taking `{ values, errors, edit }`). Bottom tabs below 768 px (`md`), sidebar from 768 px; touch targets `min-h-touch` (44 px) or more.
- Signed-in e2e specs import `test` and `expect` from `tests/e2e/auth.ts`, whose `user` fixture creates a throwaway user and deletes it (files first) after the test; take `{ user }` in the test's arguments rather than a module-level `let` set in `beforeEach`, so a failed setup never tears down the previous test's user. Sign in with `signIn(page, user, path)` through the real magic-link redirect. A second `browser.newContext()` is a second device; close extra contexts in a `finally`. Specs that don't sign in (smoke) need no Supabase.

## Lists, files and ids (from Unit 04)

- A list the app needs in full reads every page: wrap the `.range(from, to)` query in `fetchAllPages` (`src/lib/fetchAllPages.ts`, pages of 500, under `max_rows`) and give it a total order (`.order('created_at').order('id')`). See `fetchSongs`.
- Client-chosen ids use `randomUuid()` (`src/lib/randomUuid.ts`) and hashes use `sha256Hex()` (`src/lib/sha256.ts`), never `crypto.randomUUID` or `crypto.subtle` directly: both are missing outside secure contexts, which includes a phone on the LAN dev server.
- Reading a user's Guitar Pro file goes through `parseScore` (`src/features/library/parseScore.ts`), loaded with `import()`. It runs only alphaTab's Guitar Pro importers, because `ScoreLoader.loadScoreFromBytes` falls back to alphaTex and turns junk into a one-bar score. Check bytes with `checkSongFile` first, and map problems to the fixed copy in `SONG_FILE_MESSAGES`. Refuse on `file.size` before `file.arrayBuffer()`, so an oversized pick is never read into memory.
- File plus row writes (`uploadSong`, `deleteSong` in `songsApi.ts`): upload the file, insert the row, and remove the file again if the insert fails (and say so if that removal fails too). Delete the file first, then the row, so a failure leaves the song listed and retryable rather than an unreachable file. A cancel is honoured only before the insert starts.
- A drop target for files reacts only to a drag that carries files (`event.dataTransfer.types` includes `Files`, `carriesFiles` in `UploadPanel.tsx`): once the library has songs the whole list takes a dropped file, and a song card's link or selected text dragged across it must not draw "Drop the file to upload it". Component tests fire `dragOver` with `{ dataTransfer: { types: ['Files'] } }`.
- Destructive actions confirm inline in the item (`SongListItem`'s `ConfirmDelete`), with no modal, and aren't optimistic.
- Search and sort that should survive going back live in the URL (`useSearchParams`, `replace: true`), validated against a known list (`isLibrarySort`, `statsRangeFrom`). Never echo the query back as a message.
- Keep list search and sort in their own pure module (songList.ts: searchSongs, sortSongs), separate from the form module's columns and edit validation.
- Build in-app links that take a parameter with the helpers in src/lib/routes.ts (songPath(id)), not template strings. UI copy shared by two components (NO_DRUM_TRACK_NOTE) lives in a pure module, not exported from a component file.
- `tests/fixtures/gp/no-drums.gp` is a guitar-only fixture for the null `drum_track_index` path; `repeats.gp` (Unit 08) has a repeat, so two of its bars play twice.

## Player (from Unit 05)

- Every screen that plays a song uses `usePlayer` (`src/features/player/usePlayer.ts`) and the shared `PlayerControls`. The song page keeps Play/Pause (`PlayPauseButton`, with `PlayerControls showPlayButton={false}`) in a sticky bar beside the Speed/BPM readout, so both stay on screen when Play scrolls the score into view on a phone; e2e finds Play/Pause on the page, not in the controls region. Don't create `AlphaTabApi` anywhere else. `usePlayer({ fileBytes, drumTrackIndex, initialOptions })` returns `scoreRef` and `scrollRef` (render both on the first render), `player` (a `PlayerService`, null while alphaTab loads) and `snapshot`. It reads its inputs once and disposes the service on unmount, so key the component by song id to load another song.
- `PlayerService` (`PlayerService.ts`) owns playback state and talks to alphaTab only through the `PlayerEngine` interface (`playerEngine.ts`). `alphaTabEngine.ts` is the only player module that imports alphaTab, and `usePlayer` loads it with `import()`. New alphaTab features go into the engine interface first, then the service.
- Service API: `load`, `play` / `pause` / `togglePlay` / `stop`, `seekToBar`, `showBar`, `setRange({ startBar, endBar } | null)` (1-based, throws `RangeError` for bars the song lacks; validate with `isValidBarRange` first), `setLooping`, `setSpeed`, `setMetronomeOn`, `setMetronomeVolume`, `setTrackMuted`, `setDrumsMuted`, `setDrumsOnly`, `setLayout`, `setHighlight` (Unit 08, see Loops), `dispose`, and `tempoAtBar(barNumber)`. `setDrumsOnly(true)` silences every track but the drum track (`snapshot.drumsOnly`; off on open, not a setting, a no-op without a drum track). It and `drumsMuted` are never both on: turning either on turns the other off. It overrides the per-track mutes from `setTrackMuted` without changing them, so off restores what was there; send a track's mute to the engine only through `applyTrackMute`, which asks `isTrackSilenced`. `seekToBar` shows the new bar in the snapshot at once, and returns false and moves nothing for a bar outside the range that is set (alphaTab clamps such a seek but reports the bar asked for, then stops reporting positions). Typed events via `player.on('position' | 'barChanged' | 'loopWrapped' | 'finished' | 'barTapped' | 'barsDragged', handler)`, which returns its unsubscribe; call it in the effect's cleanup. `barTapped` only reports a tap on a rendered bar; the screen decides what it does (jam mode seeks, `useJamMode`), and while a loop's bars are being picked they pick bars instead (see Loops).
- Live changes (speed, metronome, mute, range, looping, layout) set engine properties only; they must never stop, play or reload. The service tests assert this with `engine.restartCalls()`.
- Call `player.play()` / `togglePlay()` straight from the click handler with nothing awaited first: iOS only starts Web Audio inside the gesture. The service also sets `navigator.audioSession.type = 'playback'` there (silent switch) and holds a Screen Wake Lock while playing (`wakeLock.ts`, best effort).
- Player failures are a `PlayerError` code mapped to fixed copy in `playerMessages.ts`; never show alphaTab's message.
- alphaTab methods that return a boolean (`load`, `loadSoundFont`) report refusal that way, with no event; check it and fail, or the page waits forever. Work the engine starts (fetches) is aborted in `destroy()`.
- A screen that unmounts its content on a query error checks `isLoadingError`, not `isError`, so a failed background refetch never tears down what is already showing (a playing song).
- Speed is a ratio clamped to the DB bounds (`speed.ts`: `clampSpeedRatio`, `ratioToPercent`, `percentToRatio`). Starting options come from `user_settings` via `playerOptionsFromSettings`; every song opens at 100%.
- Tempo and BPM (from Unit 06): `tempo.ts` (pure): `barStartTempos(score)` (the tempo each bar starts at; a mid-bar change counts from the next bar), `tempoAtBar(tempos, barNumber)`, `bpmAtSpeed(tempo, ratio)` (whole BPM). The engine sends the tempos with `scoreLoaded`; the snapshot's `barTempo` is the tempo at the current bar, so displayed BPM is `bpmAtSpeed(snapshot.barTempo, snapshot.speedRatio)`. For a loop, use `player.tempoAtBar(startBar)`.
- Taps on the score: `alphaTabEngine` listens for `click` (not pointerdown, so panning never seeks) and hit-tests with `barIndexAtPoint` (`barHitTest.ts`, pure) over `api.boundsLookup.staffSystems`. alphaTab's own interaction stays off.
- alphaTab draws its cursors unstyled. The score box carries the `jam-score` class, which `src/index.css` styles (bar and beat cursor, pointer cursor). A new score container needs that class or the cursor is invisible.
- Bars and ticks: `barTicks.ts` (`barRangeToTicks`, `barIndexAtTick`, `startTickOfBar`), working on alphaTab's tick cache in play order. Layout: `layoutForWidth` / `PAGE_LAYOUT_QUERY` (`layout.ts`, pure), page from 768 px (the stylesheet's `md`, 48rem), horizontal below; `useLayout()` (`useLayout.ts`) watches the breakpoint for React.
- Test the service and hook with `FakePlayerEngine` from `src/test/fakePlayerEngine.ts` (`finishLoading({ barTempos })`; `TEMPO_CHANGE_BAR_TEMPOS` mirrors the tempo-change fixture; `soundingTracks()` replays every mute sent and gives the tracks left sounding, which is what mute tests assert rather than the calls): `new PlayerService(engine, {...})` directly, or `usePlayer({ ..., createEngine: fakeEngineFactory(engine) })`. Fire alphaTab's events with `engine.fire(...)` or `engine.finishLoading()`, wrapped in `act` in component tests.
- Song data for the player: `useSong(id)` (row, null for no such song) and `useSongFile(id)` (bytes from Storage, `staleTime: Infinity`, under `songFileKeys`, so song edits never re-download it). The fake client answers Storage `download` through `storageResult` with `{ data: new Blob([...]), error: null }`. Check a URL id with `isUuid` before querying; Postgres errors on a malformed uuid.
- e2e for the player: `openFixture` in `tests/e2e/playerPage.ts` uploads a fixture through the library, then waits for Play to be enabled (score, MIDI and soundfont loaded) before asserting; the same file has the shared locators (`controls`, `playButton`, `muteDrumsButton`, `drumsOnlyButton`, `speedSlider`, `status`, `viewport`, `barNumber`), the score-box helpers (`scoreBox`, `barCursorBox`, `scrollScoreToStart`, `windowScrollSettled`, `untilStill`) and the layout oracle (`layoutForWidth`, `expectedLayout(page)`), so specs don't repeat the 768 px breakpoint. `jam.spec.ts` taps bars by the position of alphaTab's `.at-cursor-bar` and checks the beat cursor stays on screen while playing. `drums-only.spec.ts` reads which MIDI channels alphaTab's synth has muted by recording the `alphaSynth.*` messages posted to its worker (`recordSynthMessages`, `mutedChannels`); alphaTab never resets those mutes itself, a reload included. Those message names are alphaTab internals, so a test that reads the recorder first asserts something it must have recorded; an empty log must fail, not pass.

## Metronome sounds

- alphaTab's metronome is one hard-coded note (GM key 33, one velocity) in its synth worker, so the app plays its own: `writeMetronome` in `alphaTabEngine.ts` runs on alphaTab's `midiLoad`, takes out every `AlphaTabMetronomeEvent` and writes notes from `metronomeNotes` (`metronomeSounds.ts`, pure: sound to key in `METRONOME_SOUND_KEYS`, accent on beat one, subdivisions) on a channel no track uses (`freeChannel`). The metronome's volume and on/off are that channel's mix volume, `metronomeChannelGain(volume)` (the stored 0 to 1, squared, times `METRONOME_MAX_GAIN` 5 (3 still felt a bit quiet at 100%): at 1 it was too quiet over a band; alphaTab doesn't cap it) (`api.player.setChannelVolume`, sent again on `midiLoaded` and `playerReady`); `api.metronomeVolume` stays 0.
- It leans on alphaTab 1.9's synth in two ways: percussion samples load only for keys played on the drum channel (9), so each key the voice uses is sent there once at tick 0 with velocity 0, before every other event; and bank select 128 (CC0 1, CC32 0) then program 0 puts the drum kit on another channel. `alphaTabEngine.metronome.test.ts` renders the MIDI with alphaTab's offline exporter and the app's soundfont to prove both (node environment and 44.1 kHz: under jsdom the exporter renders NaN). Run it after an alphaTab upgrade.
- The voice (`MetronomeVoice`: `sound`, `accent`, `accentSound`, `subdivision`) is a `PlayerOptions` field from four `user_settings` columns (`metronome_sound` enum, `metronome_accent`, `metronome_accent_sound`, `metronome_subdivision`). It changes while playing too (Shane, 2026-11-27: refusing it mid-play read as a bug). A change rebuilds the MIDI (`loadMidiForScore`, which stops alphaTab); the engine's metronome track puts the tick back and, if alphaTab was playing or had been asked to play, plays again once `midiLoaded` arrives, hiding that stop and start from the service (`hidesPlayback` filters `stateChanged` and `position` until the restart's "playing"), so no session ends and the controls don't unfold. `pause()`, `stop()` and a new score call `halted()`, so nothing restarts after the user stopped. Controls use `canChangeMetronomeVoice` (the same as `canChangeOptions`). `MetronomeVoiceFields` is the one form for it, on the Settings page and in the controls bar's closed "Metronome sounds" disclosure. A new sound is a value in the enum (a migration), a key and a label.
- Settings' "Play sample" (`MetronomeSampleButton`, `useMetronomeSample`) plays two bars of the voice being chosen at the chosen volume: `renderMetronomeSample` in `alphaTabEngine.ts` (loaded with `import()` at the tap) writes the notes with `writeMetronome` and renders them offline through the player's soundfonts with alphaTab's audio exporter, then a Web Audio context of its own plays the buffer. So the sample is exactly what a song's metronome plays; never hand-draw a stand-in sound. Choosing another sound while it plays restarts it with that one; moving the volume changes the gain of the sample sounding. Like `PlayerService.play`, its tap sets the iOS playback audio session (`preferPlaybackAudioSession`) and the context's `resume()` is asked for in the tap but awaited before "playing", so a refusal is reported.

## Count-in (from Unit 07)

- Timing is pure: `countIn.ts` (`countInSchedule({ bars, meter, tempo, speedRatio, startTime })` gives click times, accents and the downbeat; `beatSeconds`, `barMeters(score)`, `meterAtBar`, `countsInEveryRepeat`). One click per beat of the meter (6/8 is six eighths). The engine sends each bar's meter with `scoreLoaded` (`barMeters`), next to `barTempos`.
- `countInRunner.ts` (`startCountIn(output, run, { onBeat, onDownbeat })`, returns a cancel) plays a schedule on a `ClickOutput` (`clickOutput.ts`). The web output is its own `AudioContext`, since alphaTab's isn't public API. Timers are only wake-ups that re-check the output's clock; never time audio off `setTimeout` alone. `PLAY_START_LEAD_SECONDS` is how early `engine.play()` is called so playback is heard on the downbeat; tune it by ear there, not in callers.
- `PlayerService` has a `countingIn` status between `ready` and `playing`, `snapshot.countIn` (`{ bar, beat, bars, beatsPerBar }` or null) for the counter, and `setCountInBars` / `setCountInMode`. Playing or counting in is "running": test it with `isRunning(snapshot.status)` from `PlayerService.ts` (Pause shown, score on screen), not the two statuses inline. A control that starts playback is enabled on `canPlay(player, snapshot)` (`controlGates.ts`: `isLoaded`, ready or running), never on `barCount` alone: the score loads before the MIDI and the soundfont, and `play()` does nothing until they are in. `pause()`, `stop()`, `setRange()` and `load()` call a count-in off; `seekToBar()` restarts it for the new bar; `setCountInBars(0)` ends it and plays at once; speed and other count-in changes apply from the next count-in. Until the engine reports `playing`, `cancelCountIn === null` under `countingIn` means the engine has already been told to play (past the downbeat): anything that halts or fails there must stop the engine too (`callOffCountIn`, used by `pause()` and `setRange()`). A user's pause or stop sets `haltRequested` until the next `play()` or `load()`, so an event already on its way from the worker (`finished`) can't restart what the user just stopped, whether it lands before or after the engine's own "stopped"; new code that starts playback from an engine event checks it. Likewise a play the service called off before the engine said "playing" (`callOffCountIn` past the downbeat sets `playCalledOff`, `startEngine()` clears it): that late "playing" is ignored while a count-in started since still clicks. Every `engine.play()` goes through `startEngine()`.
- A count-in uses the tempo and meter of the bar playback starts on, times the current speed: the bar under the cursor for Play (a mid-bar position is first moved back to its bar line), `range.startBar` for a repeat.
- "Before every repeat" works on `setRange` + `setLooping`: while it is on, the service keeps the engine's own looping off (`applyLooping`), so alphaTab stops and rewinds at the end of each pass, `loopWrapped` fires, and the service counts in and calls `engine.play()` again. Unit 08 only sets a range and looping. Don't read `engine.setLooping` as the user's choice; `snapshot.looping` is.
- Anything that must make sound later than the tap (the count-in's clicks, then `engine.play()` from a timer) is unlocked inside the tap: `play()` calls `clicks.unlock()` and `engine.unlockAudio()` before starting the count-in.
- UI: `CountInCounter` (the big number) goes inside a `relative` wrapper around the score viewport, not inside the scrolling box. Count-in copy shared with Settings is in `countInLabels.ts` (`COUNT_IN_MODE_SHORT_LABELS` for the controls bar). The controls bar's count-in is two `SegmentedControl`s (12 UX pass): the bars, and the mode only while there is a count-in.
- Tests: pass `clicks: new FakeClickOutput()` (`src/test/fakePlayerEngine.ts`) to `PlayerService` and use `vi.useFakeTimers()`; its clock follows `Date.now()`, so `vi.advanceTimersByTime` moves the count-in along. Service tests that involve a count-in or a loop start from `src/test/countInPlayer.ts` instead of building their own: `setupCountIn({ options, barTempos, meter, barMeters, loaded })`, `loopingBars5To8(setup)`, the engine steps `enginePlays` / `engineFinishesPass`, `clickOffsets`, and the timing constants (`START_DELAY_MS`, `LEAD_MS`, `BAR_MS`). `PlayerService.countIn.test.ts` has the worked examples; `PlayerService.countInEdges.test.ts` the tables (every cancel path, every moment). ## Practice sessions and progress (from Unit 09)

- Feature folder `src/features/practice/`: `sessionTracker.ts` (pure: the rules), `sessions.ts` (columns, `sessionInsert`, the history's wording: `durationLabel`, `practiceDateLabel`, `lastPracticedLabel`), `sessionKeys.ts` (import-free, like `loopKeys.ts`), `sessionsApi.ts`, `useSessions.ts`, `usePracticeTracker.ts` (the song page's glue), `LoopHistory.tsx`, and the sittings (`sittings.ts`, `visitSittings.ts`, `useVisitSittings.ts`, `VisitSummary.tsx`; see Songs first below. The On the go page it had was removed in Unit 16). The query of every loop with its song lives with the loops (`practiceList.ts`, `fetchPracticeLoops`, `usePracticeLoops`).
- What a session is, in `sessionTracker.ts`: only loop practice, only while the loop sounds (`trackerPhase`: playing with the page on show; a count-in is a gap in a session, not its end; a hidden page is stopped). Logged at a stop once it has `SESSION_MIN_PLAY_SECONDS` (30) of play time; a shorter one is kept and added to. Leaving the loop (another loop, Exit loop, the loop deleted, the screen or page left) ends it: logged if long enough, dropped if not. Editing the playing loop's bars or finishing it does not end it. Its speed is the speed at the end, its repeats are `loopWrapped` events (none while the page is hidden: the hook drops those, as the tracker drops that time). The tracker is a reducer, `observe(state, { now, loopId, phase, speedRatio }, { newId })`; new rules go there with a test, not into the hook.
- `usePracticeTracker(player, snapshot, activeLoopId)` feeds it from one effect on `[activeLoopId, status, speedRatio]`. One effect on purpose: "Play loop" on another loop changes the loop and the speed in the same render, and the tracker must see them together to log the old loop at its own speed. Don't split it or drive the tracker from `player.subscribe`.
- A session has three ways out, chosen by where the page is: the hook's mutation (`useLogSession`) while the screen stays; `logSessionUnobserved` (the same mutation run from the mutation cache) as the screen unmounts, when the hook's observer is going too; `logSessionOnExit` (a `keepalive` request) from a hidden page or `pagehide`. Both `visibilitychange` and `pagehide` are listened to (iOS often fires only the first); the first ends the session and the second finds nothing. All three send the same row and tell the caches through `sessionLogged`. A keepalive that failed is sent again through the mutation, or through `logSessionUnobserved` if the screen has unmounted since (`screenGone`): never call a hook's `mutate` after its component has gone, the mutation stays tied to the dead observer and is never collected.
- `keepaliveInsert` (`src/lib/keepaliveInsert.ts`) is the one place the app calls PostgREST without supabase-js, because supabase-js can't send `keepalive` and awaits the session before it fetches. It needs the access token in hand (`useAuth().session`, kept in a ref) and never throws. Use it only for a write that must leave from a hidden or unloading page; `supabaseRestConfig` (`src/lib/supabase.ts`) exists for it alone.
- `mutate(variables, { onSuccess, onError })` runs those callbacks for the latest call only. Where several calls of one mutation can be in flight and each needs its own answer (a retry of several unsaved sessions), use `mutateAsync(variables).then(...)` as `usePracticeTracker` does.
- Idempotent writes: a session's id is made when the session opens (`randomUuid()`), and every send is "insert, on conflict do nothing" (`upsert(..., { onConflict: 'id', ignoreDuplicates: true })`, `Prefer: resolution=ignore-duplicates`). So a retry, a keepalive that also fell back to the mutation, and Unit 11's queue can all send a record again. A foreign key error (23503) means the loop is gone: that is `loopGone`, not a failure.
- After a session is logged the server has moved the loop's `last_practiced_at`. `sessionLogged` invalidates `loopKeys.forUser` and `songKeys.forUser` (the library's "recently practiced"), each only when no write of that kind is pending, as `invalidateWhenIdle` does.
- Finish and reopen are edits of `status` through `useUpdateLoop`; `finished_at` follows in a trigger. Use `useSetLoopStatus(songId, loopId)` or the `LoopStatusButton` built on it, never `useUpdateLoop` directly: the same loop has a status control in the list, in the "Mark finished?" prompt and on the home page, and its `isPending` and `error` are read from the mutation cache (`useMutationState` with `isStatusWriteOf`), not from the control's own `useMutation`. So a press on a second control can't race the first, and a failure is still reported after the optimistic change has moved the loop to another list and unmounted the control that was pressed. Any optimistic change that moves or removes the item it was made from has this problem: a test of its failure holds the write first (`holdNext` then `failNext`), or the failure lands before React has moved anything and the test passes on a message the user would never see.
- "Mark finished?" is `hasReachedTarget(loop)` (`loopForm.ts`): the saved `speed_ratio` against `TARGET_SPEED_RATIO` (1, full speed: there is no per-loop target), compared as the whole percent the loop's line shows (`ratioToPercent`), not as the stored ratio, so 99.5% ("100%") asks. Any "has X reached Y" between values the UI shows rounded compares what is shown. It only asks; "Not yet" is remembered per loop and saved speed (`finishQuestionKey` in `LoopPanel.tsx`). The practice screen asks too, by the same rule: both call `shouldAskToFinish(loop, speedMoved)`, which also wants the speed to have moved since the loop was chosen or the loop practised before (`useSpeedMovedSinceChosen`), so a loop just saved at 100% isn't asked about. A row's bar towards the same 100% is `fullSpeedFraction` (`mastery.ts`).
- `/songs/:id?loop=<id>` opens the song on that loop (`useRequestedLoop`, `loopPracticePath()` in `src/lib/routes.ts`): checked with `isUuid`, opened once per id when the score and the loops are in, ignored when it isn't one of the song's loops. It can't start playback (that needs a tap); anything else that links into practice uses the same path. It is settled against a list read since the page opened, never one cached from an earlier visit (another device may have saved the loop or changed its speed since): the hook takes the query, waits while `fetchStatus` is `fetching` until `isFetchedAfterMount`, reads a fresh cached list that lacks the loop once more, and goes by the cache when the read fails or is paused. Anything else done once per page from a query's `data` (a default picked, an item opened) waits the same way before it latches "handled", and gives way if the user has chosen for themselves meanwhile (`userChoseLoop`).

## Keyboard shortcuts and focus (from Unit 10)

- Keys are pure rules in `src/features/shortcuts/shortcuts.ts`: `KEY_BINDINGS` (key to action), `resolveShortcut(press, { focus, helpOpen, characterKeys })` and the input guard `focusKindOf(element)` (text fields, selects and contenteditable take every key; a range slider its arrows and page keys; buttons none, so Space is play/pause wherever focus is and Enter still presses a button). Ctrl, Cmd, Alt and Shift (except `?`) are the browser's. The overlay's rows come from the same bindings (`shortcutHelp()`); a new shortcut is a binding, a help row and a case in `useSongShortcuts`, and the tests fail if the row is missing.
- Single-character shortcuts can be turned off (WCAG 2.1.4, Character Key Shortcuts: speech input types letters and punctuation with the focus anywhere). `isCharacterKey(key)` in `shortcuts.ts` is the rule (one printable character other than Space: today M, D, S, C and `?`, listed by `CHARACTER_KEYS` and written out by `characterKeysLabel()`); `resolveShortcut` takes `characterKeys` in its context and leaves such a key to the browser when it is false, and `shortcutHelp({ characterKeys })` lists only what still works. Space, the arrows and the page keys stay on: they aren't characters 2.1.4 names, and pedals need them. A new shortcut on a character key is covered by the switch with no extra code; one that must stay on with it off takes a non-character key or a modifier. The switch is per device, "Single-letter shortcuts" under "Keyboard on this device" in Settings, outside the account's form (no draft, no Save, no `user_settings` column), saved at once. Storage is `characterKeysPreference.ts` (`readCharacterKeysOn`, `saveCharacterKeysOn`, which returns false when storage refused and then holds the choice in memory for the page, and `subscribeCharacterKeys`, which hears saves in this page and the `storage` event from other tabs); every `localStorage` call there is in try/catch and anything unreadable is "on". ## PWA and offline (from Unit 11)

- vite-plugin-pwa (`vite.config.ts`, `generateSW`, `registerType: 'prompt'`) precaches the app shell, every JS chunk (alphaTab's worker and worklet too), Bravura woff2/woff, `soundfont/sonivox.sf2` and `drumkit/drums.sf3`. A new file the app fetches from its own origin must be in `globPatterns` or it won't load offline; nothing is cached at run time. A new build waits for "Reload to update" in `OfflineBanner` (`appUpdate.ts`); never `autoUpdate`, which reloads mid-practice. Once the new build takes over it controls every tab, and vite-plugin-pwa's default reloads them all; `registerServiceWorker` passes `onNeedReload`, so only the tab whose button was pressed reloads and any other keeps offering the reload (now a plain reload). Icons: `npm run icons` (`scripts/generate-icons.ts`). Playwright blocks service workers (`serviceWorkers: 'block'` in `playwright.config.ts`); a spec that needs one sets `test.use({ serviceWorkers: 'allow' })`, as `offline.spec.ts` does, and waits for `navigator.serviceWorker.ready` before going offline.
- Online state has one owner, TanStack's `onlineManager`, set up in `src/lib/network.ts` (it starts from `navigator.onLine`). Ask it with `isOnline()` in handlers and `useOnline()` in render. Every write is one of two kinds:
  - **Online only** (upload, song edit and delete, new loop, the loop edit form, loop delete, settings save, sign-out, sign-in): `networkMode: 'always'` on the mutation, the control `disabled` on `!online`, the handler refusing on `!isOnline()` (every entry point: the upload's drop zone too), and an `OfflineNote` beside it saying why. A new online-only control does all four.
  - **Queued** (session logs, `loopEditOptions` in `useLoops.ts`): default `networkMode`, so offline it pauses; `...queuedWriteRetry` (`retryNetworkFailures`, `networkRetryDelay` from `src/lib/network.ts`), so a dropped request is tried again; a refused access token (`isTokenRefusal`: PGRST301, PGRST303) is refreshed and sent again by the write's `mutationFn` (`sendRefreshingToken` in `src/lib/tokenRefresh.ts`, since supabase-js only refreshes a token whose stored expiry is near), left to the retries if the refresh had no connection, and final (`TokenRefusedError`) if the server won't refresh it; and only the server's refusal of the write (`isNetworkFailure` false: it has a Postgres code) fails and rolls back; an outbox entry put before the send (`putOutboxEntry`, started at the top of `onMutate`) and removed in `onSettled`. The options live in one function that the hook and `useOutboxReplay` (in `AppShell`) both build from: `loopEditOptions`, and `logSessionOptions` behind `logSessionUnobserved`. A queued write must be safe to send twice: a client id with "on conflict do nothing", or fields set to values. Loop edits share one `scope` per user, so they reach the server in order; a new kind of queued write that must keep its order takes a scope too.
- IndexedDB is Dexie (`src/features/offline/offlineDb.ts`): `songFiles`, `outbox`, `queryCache`. Every read and write is in try/catch and best effort (a refused database means "online only", never a broken app). A write that starts before a sign-out could land after it: read `offlineGeneration()` when the work starts and check `stillCurrent()` before writing (`songFileStore.ts`); a write made at once, with nothing awaited first, needs no check (`putOutboxEntry`). Sign-out empties it all through `AuthProvider`'s `onSignedOut` (`clearOfflineData` in `main.tsx`).
- The query cache is persisted (`PersistQueryClientProvider`, `queryPersister.ts`): every query that has data (`data !== undefined`, so a failed background refetch keeps its rows, and is restored as `success` by `asLoaded`), never `songFileKeys` (files are in `songFiles`); mutations aren't. Bump `PERSISTED_CACHE_BUSTER` when a cached row's shape changes. Restored queries are marked stale at once (`restoredCacheIsStale`), so a reload still refetches what another device changed. Default `gcTime` is `QUERY_CACHE_MAX_AGE_MS` (21 days, the persister's `maxAge`): a large query sets its own (`useSongFile`, 5 minutes). A query that can answer from the device sets `networkMode: 'offlineFirst'` (`useSongFile` via `loadSongFile`).
- Replay and sign-out (from 11 Review): `useOutboxReplay` starts only once the persisted cache is restored (`useIsRestoring`), so a replayed edit's optimistic value lands on the restored list. A replayed loop edit drops every field that an edit made on this page since it was queued has set (`editsMadeSince`; this page's own edits carry no `queueId`), and keeps its first `queuedAt` (`LoopUpdate.queuedAt`), so an older value never reaches the server after a newer one. The persisted cache is also written at once when the page is hidden or left (`saveCacheWhenHidden`, started in `main.tsx` after the restore, never before it). Anything that empties the device (sign-out) is off while `useHasUnsentWrites` (`src/features/offline/unsentWrites.ts`: pending loop writes, session logs, song uploads, edits and deletes (`songKeys.writes`) and settings saves (`settingsKeys.writes`), keepalive session logs still unanswered, counted by `startKeepaliveSend` in `src/features/practice/keepaliveSends.ts`, and any outbox entry of the user's, which is how another tab's queued writes are seen: `watchOutboxEntries`, a Dexie `liveQuery`) is true, with a note saying why, and its handler asks `hasUnsentWritesAnywhere(queryClient, userId)` at the press, then `hasUnsentWrites` again after that read. A new kind of queued write gets a mutation key that `unsentFilters` lists; a write sent round the mutation cache (a keepalive) is counted until its answer, and any fallback it starts, has been dealt with.
- The loops queries don't refetch by themselves (focus, reconnect, mount) while a loop write is pending (`refetchUnlessWritesPending` in `useLoops.ts`): a write between retries is pending but not paused, and the read would put the old row back over its optimistic value; `invalidateWhenIdle` reads them once the last write settles. A query whose rows a queued write changes does the same.
- A screen whose query has nothing cached and is paused offline says so instead of "Loading…": `waitsForNetwork(query)` (`isPending` and `fetchStatus === 'paused'`). A wait that only gates the start of something (the song page waits for settings before it opens the player, or gives way offline) is latched once it has started (`playerOpenedFor` in `SongBody`): a query that goes from paused to fetching on reconnect must not unmount what is playing.
- Auth offline: supabase-js 2.119 never emits `SIGNED_OUT` for a refresh that only lacked a network. At start with an expired token it reports `INITIAL_SESSION` null after up to 30 s of retries, so `AuthProvider` starts from the stored session when offline (`startingAuth`) and treats "null, but a session still stored" as signed in (`readStoredSession`, under `authStorageKey` from `src/lib/supabase.ts`).
- Tests: `src/test/setup.ts` loads `fake-indexeddb/auto` and after every test sets `onlineManager` online and empties the store. Go offline in a test with `act(() => onlineManager.setOnline(false))`; a network failure from the fake client is `{ message: 'TypeError: Failed to fetch', code: '' }`. Bytes read back from fake-indexeddb are another realm's `Uint8Array`: compare `Array.from(bytes)`. `src/features/offline/queuedWrites.test.tsx` has the patterns (paused then online, dropped then retried, refused, replay under StrictMode). The player's sounds retry on `online` (`PlayerService.retrySoundFont`).
- More test patterns from Unit 11's Test stage:
  - An online-only control's test goes offline, asserts it is `disabled` with its `OfflineNote`, then reaches the handler around the button (`fireEvent.submit(form)`: an Enter in a form whose submit button is disabled submits nothing, so it never reaches the guard), asserts nothing was sent after `settle()`, and finally goes online and presses it to prove the press is heard. A control with no form (a button's `onClick`) is reached by pressing it in the same `act` as `onlineManager.setOnline(false)`, before React has drawn it off: a click on a disabled button never reaches the handler (`SignOutButton.test.tsx`, "pressed before it has caught up").
  - `renderHook`'s `unmount` takes the `QueryClientProvider` with it, which unsubscribes the client from `onlineManager`, so a paused mutation would never resume. For "the screen went, the write still goes when the connection is back", call `queryClient.mount()` after the unmount (the app's signed-in layout stays) and `unmount()` it at the end (`usePracticeTracker.test.tsx`, offline).
  - An outbox entry the test's own module queued is never replayed by it (`queuedHere`, as for a page sending its own). To replay "what the last page left", write the entry to `offlineDb.outbox` directly.
  - An offline cold start in a component test: fill the cache, call `restoredCacheIsStale(queryClient)`, put the file in `offlineDb.songFiles`, then go offline and render (`SongPage.test.tsx`, "opens on a cold start offline").
  - e2e: a page loaded before the service worker took over isn't its client (`registerType: 'prompt'`, no `clientsClaim`), so a `fetch` from it skips the worker. Reload after `navigator.serviceWorker.ready` before testing what the worker answers. The persisted cache is written a second after a change, and at once when the page is hidden or left (`saveCacheWhenHidden`, best effort on an unload); still wait for it (`persistedCacheHolds`) before leaving a page whose last change a later offline step reads. Switch the connection in a spec that asserts nothing is sent offline with `recordLoopWritesWhileOffline(context)`'s `goingOffline` / `goingOnline`, which records every loop write the browser was asked to send meanwhile. `deviceData(page)` in `offline.spec.ts` reads the three IndexedDB stores. Once a write is queued offline, move between screens with the nav links (`navLink`), not `page.goto`: Chromium's offline emulation can fire `online` in the document being left while `navigator.onLine` is still false, and that document sends the queued write where Playwright's request events don't see it (13 QA). A real browser fires `online` only when the connection is back.

## Speed, target and sound (after Unit 13)

- A loop's speed is saved as it is played, with no "Save speed": `useSaveLoopSpeed(songId, activeLoop, speedRatio)` (`src/features/loops/useSaveLoopSpeed.ts`, called once on each screen that plays a loop: the jam page and the practice screen) sends a queued loop edit of `speed_ratio` for every change of the speed while a loop is active (its fields and nudges, the speed keys). It saves only a change of the speed on the same loop, never a change of loop (choosing a loop sets the player to that loop's saved speed in the same render) and never a refetch (another device's speed must not be written back over). `LoopSpeedControl` and the practice screen's `PracticeSpeed` (both through `useLoopSpeed`) read how those saves are going from the mutation cache (`useLoopSpeedSaves`, `isSpeedWriteOf` in `useLoops.ts`): "Saved on this device" while one waits offline, the latest one's failure as an alert.
- There is no per-loop target: every loop aims at 100% (`TARGET_SPEED_RATIO` in `loopForm.ts`), and the loop form has no target field.
- The drum track plays above the file's own level: `DRUM_TRACK_GAIN` (2.5, `PlayerService.ts`; the kit was really quiet under the band) through `engine.setTrackVolume`, which keeps the level and sends it again on `midiLoaded` and `playerReady`, since the synth forgets channel volumes with each new MIDI. On `playerReady` it is sent from a microtask: alphaTab 1.9 sets every rendered track back to the file's volume right after firing that event, which silently undid the boost (found by recording the `alphaSynth.setChannelVolume` messages to the worker; check any channel volume that way, the last message must be ours). Tune the gain by ear there. The cymbals (`CYMBAL_KEYS`: crashes, rides, splash, china) are some ten times quieter than the snare in MuseScore's kit, so `liftCymbals` (`alphaTabEngine.ts`, on `midiLoad`, before the metronome writes) moves their notes to a channel of their own playing the same kit, at the drum track's level times `CYMBAL_GAIN` (6; 8 was slightly too much), and silent when the drum track is muted (the channel belongs to no track, so alphaTab's mute never reaches it; `applyTrackVolumes` does it). `alphaTabEngine.cymbals.test.ts` renders a crash offline through both soundfonts to prove it hits about as hard as the snare and still rings.
- The player loads two soundfonts, in order, each over the last (`PLAYER_SOUND_FONT_URLS` in `soundFont.ts`; `engine.loadSoundFont(urls)` fetches all, then loads the first with `append` false and the rest with `append` true, and alphaTab plays a note from the last loaded font that has the instrument): Sonivox for every instrument, then MuseScore General's standard drum kit on its own (`public/drumkit/drums.sf3`, 1.3 MB, committed), because Sonivox's kit is thin. `npm run drum-kit` rebuilds it from a local `public/sf-candidates/MuseScore_General.sf3` (`scripts/extract-drum-kit.ts`, which copies one preset, the instruments and samples it reaches, and renumbers the SoundFont tables). ## How every change ships

Every change to this repo ships the way `/unit` (`.claude/commands/unit.md`) ships a unit, whether or not it is a unit: a fix, a dependency upgrade, a Dependabot or code-scanning alert, a docs or agent change. The work is finished when it is merged and GitHub shows the result, not when it passes locally, and none of these steps is a question for Shane:

1. A branch from `origin/main` (a worktree when the checkout holds other work), never the branch that happens to be checked out.
2. The change, with `npm run check` green (and `npm run build` for a dependency or config change, `npm run e2e` when behaviour changes). Commit only that change.
3. A review of the whole `git diff main...HEAD` against `docs/review-checklist.md` (the `reviewer` subagent, or the same pass by hand for a small diff); fix what it confirms.
4. Push, `gh pr create`, request Copilot's review and confirm it (unit.md, step 8).
5. Copilot's comments: verify each, fix it with a failing test first, reply on the thread and resolve it, and add a checklist row for any class no row covers. CI green.
6. Merge, then confirm the outcome on GitHub (alerts closed, the check green on `main`).

Never push a commit you didn't make without saying so first.

## Stage workflow

Each unit runs Build, Test, QA, Readability, Review (see `docs/plan.md`). Each stage:

1. Reads this file, its unit section in `docs/plan.md`, earlier notes in `docs/units/`, and `docs/review-checklist.md` (the defect classes outside reviewers keep finding: interleavings, gates, gestures, round trips, validated paths). Build designs against it, Test proves its rows, Review walks every row.
2. Stays inside its unit's scope, and holds the unit to `docs/product.md`: if the unit as written forces an order on the user, assumes a piece a song may lack (a tab, a link, loops), or adds a chore, stop and raise it rather than build it.
3. Ends with `npm run check` green (and `npm run e2e` from Unit 03 on).
4. Appends its section to `docs/units/NN-name.md`.
5. Updates this file when it sets a pattern later units should copy.
6. Adds a line to the owning unit's **Carried forward** list in `docs/plan.md` for each open issue it hands to a later unit, and deletes the lines its own unit dealt with.
