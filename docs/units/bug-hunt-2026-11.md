### Decisions

- P1 uses a flag that says "the engine was told to pause a play it hadn't reported yet", not "any playing while clicking is stale". The flag is narrower and doesn't break tests whose engine says "playing" mid-count-in. A worker more than a bar late can still fool it (Carried forward).
- P2 lives in the service, so every caller of `showBar` gets it (`useSongShortcuts`' bar step, `applyLoopRange`), not only the loop effect.
- `canPickBars` wraps `showsScoreBars`, which lives in `PlayerService.ts`: the service needs it for its event gate, and `controlGates.ts` imports the service, so the other way round would be a cycle.
- `SignOutButton`'s press is now asynchronous (one IndexedDB read) before `signOut.mutate()`. Sign-out needs no user gesture, so nothing is lost; its tests wait for the call.
- D1 holds the refetches for any loop write of the user's, not only writes to the cached list's song: the home page's list holds every loop.

### Async windows and inputs

- **Sign-out press, while the outbox is read** (`hasUnsentWritesAnywhere`): a write that starts meanwhile is caught by the second `hasUnsentWrites` after the read; going offline meanwhile, by the second `isOnline()`. A second press meanwhile starts a second read and can call `signOut.mutate()` twice (the button's `disabled` on `isPending` comes a render later); harmless, since a sign-out of an already signed-out client does nothing more.
- **`watchOutboxEntries`**: an entry written or removed by any tab re-renders the button; switching user re-subscribes, and an answer for the previous user is ignored.
- **`showBar` kept until ready**: `setRange` (a loop chosen, switched or left) drops it; a second `showBar` replaces it; `load()` of another file leaves it for the new score (only `SongPage` loads, once per mount); a soundfont failure keeps it until `retrySoundFont` brings the player to ready.
- **Between a called-off play and its late "playing"**: the new count-in's clicks go on; its downbeat calls `startEngine()`, which clears the flag, so the engine's answer to the new play is taken. Pause during that count-in calls it off as before.
- **A loop write pending (D1)**: focus, reconnect and mount refetches of the loops lists are skipped; `sessionLogged` already waited (`invalidateWhenIdle`); an explicit `refetch()` ("Try again" after a failed first load) still runs, which only happens with no rows on show.
- **A delete pressed, until the item leaves**: the list's pending focus waits up to `FOCUS_WAIT_MS` (5 s) for the item to go. A failed delete leaves the item, the finder keeps answering null, and the hand-over is let go after 5 s. If the user moves focus elsewhere meanwhile, it is left there (`useFocusWhenReady`'s rule).

### Manual verify

- Two tabs of a build (`npm run build && npm run preview`), a new build deployed or rebuilt: "Reload to update" in one reloads only that one; the other keeps playing and its banner's button then reloads it.
- Two tabs, one offline with a "Save speed" queued (DevTools offline on that tab only): Sign out in the other tab is off with "still on their way" until the first tab is back online and the edit has landed.
- Song page on a throttled connection (soundfont slow): "New loop" and Edit are enabled as soon as the score shows, taps pick bars, and jam taps don't seek until Play is enabled. Open `/songs/<id>?loop=<id>` for a loop far down the song on the same throttle: the score scrolls to it once Play is enabled.
- Laptop: start a mouse drag across bars and press Escape or Alt+Tab mid-drag (Chromium sends `pointercancel` for some of these): the highlight goes and no form opens.
- Keyboard only, library and loop panel: Edit, Cancel, Save, Delete, "Keep it", "Delete song" / "Delete loop" each leave focus on the next sensible control, never at the top of the page.
