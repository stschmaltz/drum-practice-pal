### Decisions

- P1 uses a flag that says "the engine was told to pause a play it hadn't reported yet", not "any playing while clicking is stale". The flag is narrower and doesn't break tests whose engine says "playing" mid-count-in. A worker more than a bar late can still fool it (Carried forward).
- P2 lives in the service, so every caller of `showBar` gets it (`useSongShortcuts`' bar step, `applyLoopRange`), not only the loop effect.
- `canPickBars` wraps `showsScoreBars`, which lives in `PlayerService.ts`: the service needs it for its event gate, and `controlGates.ts` imports the service, so the other way round would be a cycle.
- `SignOutButton`'s press is now asynchronous (one IndexedDB read) before `signOut.mutate()`. Sign-out needs no user gesture, so nothing is lost; its tests wait for the call.
- D1 holds the refetches for any loop write of the user's, not only writes to the cached list's song: the home page's list holds every loop.

### Async windows and inputs

- **Sign-out press, while the outbox is read** (`hasUnsentWritesAnywhere`): a write that starts meanwhile is caught by the second `hasUnsentWrites` after the read; going offline meanwhile, by the second `isOnline()`. A second press meanwhile starts a second read and can call `signOut.mutate()` twice (the button's `disabled` on `isPending` comes a render later); harmless, since a sign-out of an already signed-out client does nothing more.
- **`watchOutboxEntries`**: an entry written or removed by any tab re-renders the button; switching user re-subscribes, and an answer for the previous user is ignored.
- **`showBar` kept until ready**: `setRange` (a loop chosen, switched or left) drops it; a second `showBar` replaces it; `load()` of another file leaves it for the new score (only `SongPage` loads, once per mount); a soundfont failure keeps it until `retrySoundFont` brings the player to ready.
- **Between a called-off play and its late "playing"**: the new count-in's clicks go on; its downbeat calls `startEngine()`, which clears the flag, so the engine's answer to the new play is taken. Pause during that count-in calls it off as before.
- **A loop write pending (D1)**: focus, reconnect and mount refetches of the loops lists are skipped; `sessionLogged` already waited (`invalidateWhenIdle`); an explicit `refetch()` ("Try again" after a failed first load) still runs, which only happens with no rows on show.
- **A delete pressed, until the item leaves**: the list's pending focus waits up to `FOCUS_WAIT_MS` (5 s) for the item to go. A failed delete leaves the item, the finder keeps answering null, and the hand-over is let go after 5 s. If the user moves focus elsewhere meanwhile, it is left there (`useFocusWhenReady`'s rule).

## Copilot review

Four comments on PR #15. Each was checked against the code and, where it turned on a dependency, against the pinned source in `node_modules` or the running local stack. For the three real ones the test was written and seen failing first.

1. **`E2E_PORT` on another port: magic-link redirects fall back to the site URL.** Not real. Checked against the running auth container (GoTrue v2.198.0, whose allow-list holds only 5173 and 4173): `generateLink` with `redirectTo` `http://localhost:4183/x` and `http://127.0.0.1:4183/x` both redirected there (a 303 to the same URL). Local GoTrue accepts any port on a loopback host, which is why the earlier e2e run on 4183 passed: the specs do rely on the redirect (`signIn` waits for the redirected path). The probe was a throwaway script that made and deleted its own user. `supabase/config.toml` is unchanged, so no restart is needed. AGENTS.md's `npm run e2e` row now says any port works and why. A LAN host on another port would not be allowed, but e2e never uses one. Checklist row: none.
2. **A saved rename that leaves the library search drops focus.** Real: the item's own hand-over to its Edit lived in the item, which unmounted once the form closed and its `editingIds` pin went. Test: `LibraryPage.test.tsx`, "focus after a rename that leaves the search": to the search field when nothing is left on show, to the next song's Edit when others are (both failed before), and on its own Edit when it still matches (passed before, kept). Fix: `SongListItem` takes `onEditClosed`; given it, the list hands focus on (`followEditClosed` in `LibraryPage`'s `SongList`): the song's own Edit once it is back, nothing while the form still shows, else the next song's Edit (from the list as it was at the press) or the search field. Checklist row: "Focus when a control replaces itself", widened to the item leaving a filtered list.
3. **`showBar` dropped when the sounds are ready before the score renders.** Real: `readyForPlayback` cleared `pendingShowBar`, and the engine's `scrollToBar` returned quietly with no bounds. Tests: `PlayerService.showBar.test.ts`, "asked once the sounds are in but before the notation has rendered" (five cases: kept from loading, asked when ready, a `setRange` drops it, playing by then, a count-in started before the render; three failed before); `alphaTabEngine.pointer.test.ts`, "says whether it could decide" and "reports each finished render as rendered". Fix: `PlayerEngine.scrollToBar` returns false while the score has no bounds (no surface, or no staff systems) and true once it could decide, a bar the score lacks included. A new engine event, `rendered` (alphaTab's `postRenderFinished`). The service keeps the bar when the engine says false (`scrollToBarWhenRendered`, also used by a count-in's scroll) and asks again on `rendered` through `showBar`'s own rules (not while playing, dropped by `setRange`). `FakePlayerEngine.laidOut` says whether its `scrollToBar` can. Checklist row: "Asked before it can be done, then forgotten", widened to a "ready" that comes in two parts.
4. **Retrying PGRST301 resends the same refused token.** Real. In `@supabase/auth-js` 2.119.2, `__loadSession` refreshes only when the stored `expires_at` is within `EXPIRY_MARGIN_MS`, so a token refused for a bad signature (or by a server whose clock is ahead) went again unchanged at every retry, and the loop edits' shared `scope` and sign-out's "pending" gate waited behind it. Tests: `src/lib/tokenRefresh.test.ts` (new, eight cases); `useLoops.test.tsx`, "a token the server refuses is refreshed, and the edit sent again with the new one" and "a token that can't be refreshed fails the edit and rolls it back" (both failed before). Fix: `sendRefreshingToken` (`src/lib/tokenRefresh.ts`) wraps the `mutationFn` of both queued writes (`loopEditOptions`, `logSessionOptions`). On a token refusal it calls `supabase.auth.refreshSession()` and sends once more, at once. A refresh with no connection (`isAuthRetryableFetchError`) rethrows the token refusal, which `retryNetworkFailures` still retries (paused offline, so the write stays queued). A refused refresh, or the new token refused too, throws `TokenRefusedError` (code `token_refused`, fixed copy), which isn't retried: the edit rolls back, and a session log is answered as refused. The pure helpers in `network.ts` are unchanged apart from their comments. Checklist row: "What counts as a refusal", widened: a retry must change what was refused.

### Decisions

- 2: the next song's Edit comes before the search field, in the same order as a delete's hand-over (the next item's control); the search field only when the list is empty. The item keeps its own hand-over when no list is given (its own tests render it alone).
- 3: the retry lives in the service, not the engine, so the "not while playing" and "a `setRange` drops it" rules apply to it as well. A bar the score lacks counts as decided, so a pending bar can't be asked again on every render for ever.
- 4: a refused refresh fails the write rather than signing out. supabase-js keeps the session while the access token's stored expiry hasn't passed, and a sign-out from inside a mutation would run into the sign-out gate, which counts that very write as pending. The user sees "Your sign-in has expired. Sign in again to save this." in the write's error. The refresh and the one resend are inside `mutationFn`, so they don't wait for the retry delay and add no retries of their own.

### Async windows and inputs

- **Between `readyForPlayback` and `rendered`** (comment 3): a `showBar` keeps its bar; a later one replaces it; `setRange` drops it; Play with a count-in keeps the count-in's bar the same way; Play with no count-in, then `rendered`: `showBar` is a no-op while playing, and the bar is dropped. Later renders (resize, layout) find nothing pending.
- **A token refused, while `refreshSession` runs** (comment 4): other loop edits wait behind it in the `scope`; going offline makes the refresh fail as retryable, so the write is kept and resumes on reconnect; a sign-out from another tab makes the refresh fail as refused (no session), so the write fails and rolls back.
- **A saved rename, until the list re-renders** (comment 2): the list's pending focus waits while the form shows (the item is listed, its Edit isn't), and up to `FOCUS_WAIT_MS` if the save fails and the form stays; focus moved elsewhere meanwhile is left there.

### Known gaps

- After a `TokenRefusedError` the user is still signed in with a session the server won't take; every queued write fails the same way until they sign out and in again.
